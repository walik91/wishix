# Wishix

Нужны Docker и Docker Compose 2.22+. Все команды выполнять из корня проекта.
Общий порт страницы и API задаётся в `.env`: сейчас `APP_PORT=5173`.

Параметры БД тоже в `.env`: `DB_NAME`, `DB_USER` и `COCKROACH_IMAGE`. По указанию владельца CockroachDB запускается с `--insecure`: TLS и проверка паролей отключены. Первый запуск создаёт БД и пользователя; данные сохраняются в постоянном томе после обычного `docker compose down`. Существующий `DB_PASSWORD` в `.env` сохраняется, но не используется.

Compose-проект и сеть используют имя `wishix`, контейнеры и образы приложения — префикс `wishix-`. В `.env` заданы `DB_NAME=wishix` и `DB_USER=wishix`. Данные хранятся в томе `wishix_db-data`; ранее созданные тома сертификатов не удаляются.

## Разработка

```sh
docker compose up --build --watch
```

Открыть <http://localhost:5173>. Изменения Vue сразу появляются в браузере, Go автоматически пересобирается. Логи видны в терминале; `Ctrl+C` останавливает запуск.

Гостевая главная: <http://localhost:5173/>. Рабочая регистрация и вход: <http://localhost:5173/register> и <http://localhost:5173/login> (`/sign-up` и `/sign-in` открывают соответствующие экраны). Регистрация требует подтверждения email кодом из письма; после подтверждения и входа открывается `/my`. Восстановление — `/forgot-password`. Сессии хранятся на сервере, выход и сброс пароля отзывают их. Страницы адаптивны и поддерживают EN/RU/RO. Google доступен при настройке провайдера. Facebook исключён из текущих планов, хотя существующий код сохранён и при полной конфигурации может включить вход.

В `.env` также нужны `APP_ORIGIN`, `AUTH_SECRET`, `AUTH_TRUSTED_PROXY_CIDRS` и настройки `SMTP_*`. При локальной разработке origin может быть `http://localhost:5173`; для тестирования через туннель — его внешний HTTPS-адрес. SMTP предоставлен владельцем Zoho через STARTTLS. `AUTH_SECRET` создаётся один раз и сохраняется между запусками. Подробности настройки, API, предложенных параметров паролей/кодов и проверок — в [docs/AUTH.md](docs/AUTH.md). При старте сервер автоматически выполняет Goose `up`; HTTP запускается только после успешных миграций.

## Миграции Goose

Отдельная консольная команда собирается в Docker вместе с API. Для применения и проверки версии:

```sh
docker compose run --rm --build migrate up
docker compose run --rm migrate status
docker compose run --rm migrate version
```

Явный откат последней миграции: `docker compose run --rm migrate down`. Перед откатом остановить API: `docker compose stop server`. **Down первой миграции удаляет аккаунты и связанные данные.** Следующий запуск текущего API снова выполнит автоматический up; для работы на старой схеме сначала вернуть соответствующую версию кода. Есть также `up-by-one`, `up-to VERSION`, `down-to VERSION`, `redo`, `reset`.

Для production добавить `-f compose.prod.yaml` сразу после `docker compose`. Подробности перехода со старой схемы, проверки пустой БД и написания новых миграций — в [docs/MIGRATIONS.md](docs/MIGRATIONS.md).

Прежняя техническая страница проверки соединения сохранена по адресу <http://localhost:5173/status>.

Гостевые страницы используют общий layout: шапку с навигацией, контейнер шириной до 1120 px и подвал. После входа в гостевой шапке появляется «Моё». Ссылки «Как это работает» и «Вопросы» ведут к разделам главной.

Общая главная `/` доступна гостям и авторизованным пользователям. После входа на ней остаётся кнопка «Моё», а обе основные кнопки меняются на «Перейти к моим желаниям» и ведут на `/my/wishes`. Гостю они предлагают регистрацию. Успешный вход и подтверждение регистрации открывают «Моё»; сам переход на `/` больше не вызывает перенаправление.

У `/my` собственная оболочка по дизайн-системе: боковая навигация на desktop, нижняя — на mobile/tablet. Это обзор личного пространства с реальными списками и последними желаниями, ссылками на полные разделы и созданием списка. Пункт «Мои желания» открывает коллекцию `/my/wishes`: можно добавить желание на отдельной странице `/my/wishes/new` и удалить его с подтверждением. Название обязательно; изображение, описание, примерная цена с валютой и магазинные ссылки необязательны. Первая ссылка однократно запускает автоматический импорт через общий парсер; кнопку рядом с любой ссылкой можно использовать для импорта из неё. Ручные правки сохраняются, ошибки не мешают ручному добавлению. Изображение JPEG/PNG/WebP до 5 МБ можно выбрать с предпросмотром; нажатие на миниатюру карточки позволяет загрузить, заменить или удалить его у сохранённого желания. Данные и изображения хранятся в CockroachDB; общая коллекция закрыта по умолчанию, владелец может открыть её отдельным флажком профиля. Желания в доступных списках видны их посетителям. Текстовые поля, цену, приоритет и ссылки сохранённого желания можно редактировать с карточки; изменения видны во всех списках. Подробности — в [docs/WISHES.md](docs/WISHES.md), [docs/WISH_IMAGES.md](docs/WISH_IMAGES.md) и [docs/URL_IMPORT_PROPOSAL.md](docs/URL_IMPORT_PROPOSAL.md).

Раздел «Списки» `/my/lists` позволяет создавать, редактировать, копировать, очищать и удалять списки, выбирать их желания и менять доступ. При добавлении желания внутри списка он выбран автоматически. Копия списка сохраняет общие неполученные желания; отметка «Получено» действует в конкретном списке; очистка и удаление не удаляют их из коллекции. Публичный список доступен без регистрации по `/u/{username}/wishlist/{id}`, а список по ссылке — по `/u/{username}/wishlist/{id}/{token}`. При смене username ссылка перенаправляется сервером на актуальный адрес с HTTP 301. Публичный профиль `/u/username` показывает публичные списки и ссылку на коллекцию, если она открыта. Токен сохраняется при смене режима; ссылку можно обновить вручную с подтверждением. Личный режим закрывает гостевой доступ. См. [docs/LISTS.md](docs/LISTS.md).

В доступном списке гость может забронировать подарок без аккаунта после подтверждения email кодом. Если на этот адрес уже зарегистрирован аккаунт, после подтверждения кода приложение предложит в него войти. Открытая общая коллекция служит для просмотра и не поддерживает бронирование или отметку получения. Ссылка из письма позволяет управлять бронью и покупкой. Бронь относится к желанию во всех списках, а купленный подарок другим виден как забронированный. Списки с прошедшей датой закрываются для гостей. При изменении даты и удалении списка или желания дарители получают уведомления; необязательное сообщение автора можно добавить при удалении списка. Доставка и повторные попытки используют очередь в БД. Сроки, ограничения и оговорка о часовом поясе старых списков описаны в [docs/RESERVATIONS.md](docs/RESERVATIONS.md).

Username и email берутся из текущей серверной сессии. Из окна «Профиль» доступны настройки имени, фото, возраста, описания и их публичности, смена username и управление открытостью коллекции. В «Поиске» авторизованный пользователь находит людей по username или публичному имени; в профиле другого человека можно подписаться, заблокировать его или оставить жалобу. Списки подписок и подписчиков доступны владельцу и другим людям в соответствии с настройками. Жалобы сохраняются в БД; панели модерации пока нет. Демонстрационные данные не подставляются. Подробности — [docs/SEARCH.md](docs/SEARCH.md) и [docs/PROFILE_SOCIAL.md](docs/PROFILE_SOCIAL.md).

Проверка API и соединения с БД: <http://localhost:5173/api/ready>.

После изменения `.env`, Docker-конфигурации или зависимостей остановить и повторить команду запуска.

## Подключение DBeaver

В обоих режимах SQL-порт CockroachDB публикуется только на `127.0.0.1:26257` компьютера с Docker. При уже запущенном проекте применить настройку можно командой `docker compose up -d --no-deps db`; для production использовать `docker compose -f compose.prod.yaml up -d --no-deps db`. Контейнер БД будет пересоздан, данные в томе сохранятся, а соединения кратковременно прервутся.

### На компьютере с базой

В DBeaver создать подключение CockroachDB: host `127.0.0.1`, port `26257`, database и username взять из `DB_NAME` и `DB_USER` в `.env`. Пароль оставить пустым, SSL выключить. SSH на том же компьютере не нужен.

### К базе на удалённом сервере

На компьютере с DBeaver открыть SSH-туннель и оставить терминал работающим:

```sh
ssh -L 127.0.0.1:26258:127.0.0.1:26257 SSH_USER@SERVER
```

В DBeaver указать host `127.0.0.1`, port `26258`, имя базы и пользователя из `.env` сервера; пароль оставить пустым и SSL выключить. При занятом локальном порте `26258` выбрать другой в команде и DBeaver. Подключение к SSH-серверу требует настроенного доступа и проверки его ключа. SSH шифрует туннель, но CockroachDB в режиме `--insecure` не проверяет пароли: любой, кто может подключиться к локальному порту на сервере или по Docker-сети, может войти в том числе как `root`.

## Тестирование через Cloudflare Tunnel

Для туннеля укажите в `.env` его публичный HTTPS-адрес в `APP_ORIGIN` и секретный токен в `CLOUDFLARE_TUNNEL_TOKEN`. Файл `.env` исключён из Git; не публикуйте токен и не передавайте его в чат. Затем запустите обычный режим разработки:

```sh
docker compose up --build --watch
```

Маршрут Cloudflare Tunnel должен направлять запросы на `http://127.0.0.1:5173`: контейнер `cloudflared` использует сетевое пространство фронтенда и обращается к внутреннему порту Vite. Явный IPv4-адрес важен: `localhost` может разрешиться в IPv6-адрес `::1`. Туннель стартует вместе с проектом после готовности фронтенда и останавливается вместе с ним; ПК и Docker должны работать. Vite разрешает hostname из `APP_ORIGIN`; сам адрес не закреплён в коде. После изменения `.env` повторите команду запуска. Из-за текущей конфигурации прокси посетители туннеля делят IP-лимиты приложения; клиентские IP-заголовки извне не считаются доверенными.

## Запуск на сервере

Скопировать проект на сервер с Docker и настроить `.env`. Указать `APP_ORIGIN=https://<выбранный-хост>` и настроить внешний HTTPS-прокси, который направляет запросы на `APP_PORT`. Production требует HTTPS-origin для Secure-cookie и зашифрованный SMTP. Внешний домен в коде не закреплён.

```sh
docker compose -f compose.prod.yaml up -d --build
```

Приложение доступно по настроенному HTTPS-адресу. Vue собирается и раздаётся через Nginx; `/api*` обрабатывает Go. Контейнеры работают в фоне и перезапускаются вместе с Docker. Для обновления скопировать новый код и повторить ту же команду.

БД работает на одном узле вместе с приложением; отказоустойчивый кластер и автоматическое резервное копирование ещё не настроены.

Ручная полная копия БД и восстановление в отдельную базу: [docs/DATABASE_BACKUP.md](docs/DATABASE_BACKUP.md). Автоматические резервные копии не настроены.

Логи и остановка:

```sh
docker compose -f compose.prod.yaml logs -f
docker compose -f compose.prod.yaml down
```
