# AGENTS.md — Wishix

## О проекте
Wishix — международный веб-сервис списков желаний и организации подарков. Пользователь хранит желания, объединяет их в списки, делится ссылками; дарители просматривают списки и бронируют подарки, в том числе без регистрации. В перспективе — платформа поиска подарков и партнёрств с магазинами.

**Язык рабочей документации:** русский. **Языки интерфейса на старте:** английский (`en`), русский (`ru`), румынский (`ro`). Базовый язык локализации — английский.

**Основной источник продуктовых требований:** [`docs/PROJECT.md`](docs/PROJECT.md).  
**Технические решения и архитектура:** [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

Название продукта и интерфейса — **Wishix**. Домен для нового названия пока не выбран; не привязывать инфраструктуру к предполагаемым доменам.

## Правила работы Codex

1. **Сначала прочитай** `docs/PROJECT.md` и `docs/ARCHITECTURE.md` перед архитектурными решениями или задачами, затрагивающими бизнес-логику.
2. **Не меняй согласованные правила продукта молча.** Если задача противоречит `docs/PROJECT.md`, укажи конфликт и предложи минимальное изменение. Новые решения отмечай как «предлагается» до одобрения владельцем проекта.
3. **Не придумывай готовый стек.** Выбор frontend/backend/БД/деплоя обсуждается отдельно; после утверждения запиши решения в `docs/ARCHITECTURE.md`.
4. **Двигайся небольшими вертикальными этапами** (рабочий пользовательский сценарий с интерфейсом, API, хранением и проверкой), а не создавай сразу огромный каркас из заглушек. Избегай преждевременной сложности.
5. **При изменении бизнес-логики обновляй документацию в той же задаче.** `docs/PROJECT.md` — поведение продукта; `docs/ARCHITECTURE.md` — техническая реализация. Не превращай `AGENTS.md` в дублирующее ТЗ.
6. **До начала существенной реализации** предложи краткий план, границы задачи и критерии готовности. Для мелких правок можно сразу действовать.
7. **Не стирай существующие решения и данные.** Изменения схемы БД — через миграции; деструктивные изменения и опасные команды требуют явного согласования.
8. **Поддерживай тесты для критичной логики**, особенно бронирований, контроля доступа, сроков, лимитов и копирования/удаления списков. После изменений запускай релевантные проверки и сообщай результат.
9. **Избегай переусложнения:** AI-рекомендации, каталог товаров, встроенные платежи, нативные приложения и коммерческие интеграции не входят в первую версию.
10. **Проектируй интерфейс mobile-first**, но поддерживай полноценную desktop-версию. Текст интерфейса — через локализацию, не вшивать строки в компоненты.
11. **Каждая завершённая задача — отдельный коммит.** После релевантных проверок фиксируй изменения задачи в локальном Git с понятным сообщением. Удалённый репозиторий не настраивать без отдельной команды владельца проекта.

## Инварианты, которые нельзя нарушать

- У одного пользователя есть единая коллекция желаний. Одно желание может быть в нескольких списках; независимая копия создаётся только явным действием пользователя.
- Бронь относится к **желанию**, а не к записи о желании в конкретном списке: один подарок нельзя одновременно забронировать через два списка.
- Просмотр списков и гостевое бронирование по разрешённой ссылке работают **без обязательной регистрации**. Для бронирования email обязателен и подтверждается кодом; если после подтверждения обнаружен существующий аккаунт с этим email, для бронирования нужно войти в него.
- Остальным дарителям и в публичных ответах показываем одинаковую доступность «Забронировано» для броней со статусом «Забронировано» и «Куплено». В интерфейсе владельца информация о бронированиях/покупках скрыта. Гарантировать полную тайну при анонимном гостевом доступе невозможно.
- В одном списке допускается максимум **4 активные гостевые брони на подтверждённый email**. Лимит относится к списку, через который создана бронь; общая коллекция информативна и бронирования не поддерживает. Не показывать в UI внутренний механизм расчёта. Купленные подарки занимают слот; отменённые и истёкшие — нет.
- Новые списки имеют режим «По ссылке» по умолчанию. Публичность общей коллекции «Все желания» управляется **одним отдельным флажком профиля** (по умолчанию выключен), без собственных режимов «по ссылке / публичный».
- Ручное добавление желания всегда доступно, в том числе вообще без ссылок на магазины. Магазинных ссылок может быть несколько; первая используется для первоначального автозаполнения, остальные — альтернативные места покупки.
- Списки **не архивируются**. Удаление — с предупреждением и подтверждением; возможно необязательное сообщение дарителям.
- Парольные аккаунты требуют подтверждения email кодом. В MVP также предусмотрен вход через Google. Facebook исключён из текущих планов, существующий код сохраняется; Apple и Instagram — позже.

## Безопасность и приватность — обязательно учитывать при реализации

- Проверять права доступа **на сервере** для всех операций. Режимы списка: личный / по ссылке / публичный. Подписка на человека не открывает личные списки.
- Бронирование должно быть атомарным: конкурентные запросы не должны создавать две действующие брони на одно желание. Изменение статуса, продление и лимиты также проверять на сервере.
- Секретные ссылки/токены управления бронями не должны попадать в логи, публичные API или поисковые индексы. Способ передачи и хранения токенов уточнить при проектировании.
- При загрузке товара по URL защищаться от SSRF, доступа к внутренним адресам, бесконечных редиректов, слишком больших ответов и небезопасных файлов. Не считать метаданные магазина доверенными.
- При использовании IP-ограничений учитывать reverse proxy и доверенные заголовки; нельзя слепо доверять переданному клиентом `X-Forwarded-For`.
- Приватные поля профиля не возвращать в публичном API и не индексировать. Включение «Показывать все желания» действительно делает общую коллекцию доступной всем: предупреждать пользователя.
- Блокировка аккаунта не гарантирует защиты от анонимного посетителя. CAPTCHA предназначена для ботов, не для защиты от намеренного бронирования человеком.


## Дизайн-система Wishix обязательна для UI-работ

- До UI-задач прочитать `docs/DESIGN_SYSTEM.md`, `docs/RESPONSIVE_AND_SCREENS.md`, `docs/AI_IMPLEMENTATION_GUIDE.md` и посмотреть изображения `docs/design/reference/original-desktop-mobile.png`, `docs/design/reference/approved-brand-board.png`.
- Использовать `docs/design/tokens.css` или те же значения в эквивалентном формате выбранного стека. Не изобретать новую палитру или параллельную библиотеку элементов.
- Главный визуальный образ — фиолетовый подарок с белым сердцем; допустима утверждённая векторная адаптация из `docs/design/assets/`, но не emoji и не случайная generic gift-иконка вместо логотипа.
- Название интерфейса и wordmark — **Wishix**. Обнаруженные в текущем коде упоминания старого названия заменять **там, где это часть брендинга**, с учётом существующей архитектуры и без изменения истории миграций/юридических данных без команды.
- Desktop и mobile — адаптивные представления одних сущностей, а не два несогласованных интерфейса.
- Реализовать общие компоненты: AppShell, Navigation, Button, Card, ListCard, WishCard, Input, Dialog/Sheet, Badge, EmptyState, Toast/Skeleton. Не внедрять новые функции по одной лишь картинке.
- Учитывать hover, pressed, focus-visible, disabled, loading, empty, error и длинные тексты. Минимальная размерность важных touch-целей — 44×44 CSS px.
- Проверять ширины 320, 390, 768, 1024 и 1440 px, наличие горизонтального overflow и работу нижней навигации с safe area.
- Названия демонстрационных карточек, цены/валюта, аватар Анны и счётчики списков — **только визуальные примеры**, не доменная модель и не бизнес-правила.
- Если концепт дизайна расходится с утверждённым `docs/PROJECT.md`, приоритет у продуктовой спецификации. Отмечать спорные детали и не принимать решение самовольно.
- Стек не определён дизайн-системой. Наличие HTML/CSS-превью не является требованием использовать определённый framework.
- Не добавлять корзину, checkout, маркетплейсный каталог или подписки только потому, что похожие блоки бывают в готовых ecommerce-шаблонах.
