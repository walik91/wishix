# Управление желаниями — первый рабочий этап

**Объём утверждён владельцем 2026-11-04:** просмотр общей коллекции, ручное добавление и удаление желания. Последующим поручением добавлено [управление списками](LISTS.md) с общими желаниями.

Дополнительно по поручению владельца реализована загрузка одного необязательного изображения и управление им у сохранённого желания. Хранение, API и предлагаемые ограничения — в [WISH_IMAGES.md](WISH_IMAGES.md).

По поручению владельца первая магазинная ссылка автоматически запускает одну попытку импорта общим парсером; любую ссылку можно импортировать кнопкой рядом с ней. Поведение, API, безопасность и расширение адаптерами — в [URL_IMPORT_PROPOSAL.md](URL_IMPORT_PROPOSAL.md).

## Поведение

- `/my` показывает обзор личного пространства с реальными списками и последними желаниями. Пункт «Мои желания» открывает `/my/wishes` с полной коллекцией текущего аккаунта, новые желания сверху. Пустая коллекция, загрузка и недоступность сервера имеют разные состояния.
- `/my/wishes/new` — отдельная страница добавления. Обязательно только название; описание, примерная цена с валютой и магазинные ссылки необязательны. Приоритет — низкий, средний или высокий.
- С карточки желания в коллекции или списке можно открыть редактирование названия, описания, цены, валюты, приоритета и магазинных ссылок. Сохранение меняет одно общее желание во всех списках; изображение и состав списков управляются отдельно с карточки. При конфликте с изменением в другой вкладке форма сохраняет введённые данные и предлагает загрузить актуальную версию с предупреждением об их потере. Изменение ссылок не запускает импорт.
- В форме добавления сначала видны необязательная ссылка на товар, название, место сохранения и кнопка «Сохранить желание». Дополнительные ссылки открываются по кнопке «Добавить ещё ссылку». Изображение, описание, цена с валютой и приоритет раскрываются по кнопке «Добавить детали». При ошибке в скрытом поле форма раскрывает детали и переводит фокус к первому полю с ошибкой.
- В блоке «Примерная цена» можно выбрать MDL, RON, EUR и другие валюты или ввести другой трёхбуквенный код. Новое желание получает последний ручной выбор для аккаунта в этом браузере. Импорт из магазина подставляет свою пару суммы и валюты, пока поля не изменены вручную. При редактировании начальная валюта берётся из желания.
- Место сохранения показывает «Все желания» и выбранные списки. При открытии формы из списка он выбран заранее. Выбор можно изменить через «Списки желания».
- Сохранение возвращает к коллекции с уведомлением, а при создании в выбранном текущем списке — в этот список. Данные читаются из БД, сохраняются после перезагрузки и повторного входа.
- Удаление требует подтверждения с названием желания и предупреждением о необратимости. До успешного ответа карточка остаётся в коллекции; при ошибке доступен повтор. Удаление последнего желания открывает пустое состояние.
- Общая коллекция закрыта по умолчанию и открывается отдельной настройкой профиля. Желание можно выбрать для нескольких списков при создании и изменить членство позже. Гости видят желания и изображения из разрешённого списка или открытой коллекции, но бронировать можно только в списке; подробности — [RESERVATIONS.md](RESERVATIONS.md). Отметка «Получено» действует в конкретном списке. При создании ссылка может заполнить название, описание, изображение и примерную цену/валюту; ручные правки сохраняются. Первая ссылка импортируется автоматически, любая другая — по кнопке. Ошибка импорта не блокирует ручное создание.
- С карточки в коллекции или списке владелец может создать независимую копию в общей коллекции. Копируются название, описание, цена, валюта, приоритет, ссылки и изображение; исходное желание не меняется. **Предлагается:** копия изначально не входит в списки, принадлежность выбирается отдельно. Отметки получения и бронирования не копируются; у новой записи собственный ID и независимые бронирования. Если коллекция опубликована, копия также будет в ней видна.

## Рабочие параметры — предлагается

Это ограничения текущей реализации для проверки владельцем, а не новые окончательные правила MVP:

- Название — 1–200 символов Unicode после обрезки пробелов по краям; описание — до 500. При импорте длинное описание сокращается; в карточке показываются первые три строки, полный текст открывается в отдельном окне для владельца и гостей. Карточки желаний в одной сетке имеют одинаковую высоту. Существующие длинные описания сохраняются, но перед сохранением правок их нужно сократить до нового лимита. Нулевой символ запрещён.
- Приоритет по умолчанию — средний.
- Цена — от 0 до 9 999 999 999,99, до двух знаков после разделителя. Форма принимает точку и запятую; API принимает десятичную строку с точкой. Цена не хранится как число с плавающей точкой. Без цены валюта не сохраняется; при наличии цены нужен трёхбуквенный код `A–Z`.
- До 10 упорядоченных ссылок, каждая до 2 048 байт UTF-8. Только абсолютные HTTP(S)-адреса без пробелов, управляющих символов и учётных данных. Ссылки открываются с `noopener noreferrer`; в форме создания импорт доступен для каждой ссылки. Сохранение и открытие карточки не обновляют метаданные.
- Список пока возвращает всю коллекцию без пагинации и искусственного лимита количества желаний.

## Хранение и API

Goose-миграция `002_wishes.sql` добавляет `wishes` и `wish_shop_links`. Желание принадлежит аккаунту напрямую; системная коллекция не создаёт обычный список. У ссылки составной ключ `(wish_id, position)`. Удаление желания удаляет его ссылки и членство во всех списках через внешние ключи, не затрагивает аккаунты или другие желания. Индекс `(owner_id, created_at DESC, id DESC)` задаёт устойчивый порядок.

| Метод и путь | Результат |
|---|---|
| `GET /api/wishes` | `200 {"wishes": [...]}`; пустая коллекция — `[]` |
| `POST /api/wishes` | `201 {"wish": {...}}` |
| `POST /api/wishes/{id}/copy` | `201 {"wish": {...}}` — независимая копия принадлежащего владельцу желания; тело `{}` |
| `GET /api/wishes/{id}` | `200 {"wish": {...}}` для владельца |
| `PUT /api/wishes/{id}` | `200 {"status":"ok"}` при успешном изменении |
| `DELETE /api/wishes/{id}` | `200 {"status":"ok"}` |

Поля JSON POST: `title`, `description`, `price` (строка либо `null`), `currency`, `priority`, `shop_links` (массив строк), `list_ids` (необязательный массив ID списков владельца). С изображением POST использует multipart с JSON-полем `wish` и файлом `image`. DTO ответа содержит `id`, те же текстовые поля, `created_at` и `image_url` (либо `null`), без бинарных данных, `owner_id`, данных аккаунта или будущих сведений о бронях.

PUT принимает редактируемые поля и `edit_version` из ответа GET, без `list_ids` и изображения. Сервер проверяет владельца и версию, валидирует поля как при создании и атомарно обновляет желание и ссылки в retry-транзакции. Версия вычисляется по редактируемым полям, поэтому независимые изменения изображения или членства в списках не вызывают конфликт. Устаревшая версия получает `409 wish_conflict`; отсутствие или чужой ID — `404 wish_not_found`. Брони и связи со списками не меняются.

Копирование считывает исходные поля, ссылки и изображение и сохраняет отдельную запись с новым ID и версией изображения в одной retry-транзакции; повтор создаёт свежие модели. Чужой, некорректный или отсутствующий ID возвращает `404 wish_not_found`. Связи списков и бронирования не копируются. Неопределённый результат сетевой ошибки требует проверить коллекцию перед повтором.

Контроллер проверяет существующую cookie-сессию для каждой операции; `owner_id` берётся только из неё. Чужое, отсутствующее или некорректное ID при удалении возвращает одинаковый `404 wish_not_found`. Тело не может переопределить владельца: неизвестные поля JSON отклоняются. Без сессии — 401, при сбое хранения — обобщённый 503.

POST/PUT/DELETE требуют настроенный `Origin`, `X-Wishix-Request: 1`, разрешённый Content-Type и отсутствие `Sec-Fetch-Site: cross-site`. JSON ограничен 48 КиБ, лишние JSON-значения отклоняются. Multipart для изображений имеет отдельные ограничения из WISH_IMAGES.md. Все ответы приватного API имеют `Cache-Control: no-store`. Содержимое желаний, файлов и ссылок не записывается в сообщения об ошибках.

Сервис → предметный репозиторий с общим `Base.Ctx(ctx)`. Создание желания и всех ссылок происходит в одной retry-транзакции; модели пересоздаются при каждом повторе. Удаление проверяет владельца непосредственно в SQL `WHERE id = ? AND owner_id = ?`. Точный жизненный цикл удаления при появлении броней будет согласован перед их реализацией.

Фронтенд использует существующий AppShell и дизайн-токены. `api/wishes.js` содержит запросы, `useWishes` — загрузку/удаление, `MyPage` и `NewWishPage` — экраны. `WishCard` отображает реальные данные. Общие TextField, Dialog, Button, Skeleton и Toast поддерживают состояния формы и подтверждения. Интерфейс переведён на EN/RU/RO.

## Проверки

```sh
docker compose -f compose.auth-test.yaml run --rm go-tests
docker compose -f compose.auth-test.yaml exec -T front npm run build
```

Сборка server выполняет `go vet ./...` и `go test ./...`. Интеграционные тесты используют отдельную тестовую CockroachDB и случайные схемы: отсутствие доступа без сессии, изоляция двух владельцев, корректное сохранение и порядок, десятичная цена, несколько ссылок, защита от CSRF, некорректный/большой JSON, удаление ссылок, откат частичного создания. Миграционные тесты проверяют повторный Up и откат новой схемы с сохранением аккаунтов.

`TestIntegrationIndependentWishCopy` проверяет права, атомарный откат копии, перенос полей и изображения, независимость изменений и удаления и возможность отдельно забронировать оригинал и копию. `front/tests/wish-copy.browser.mjs` проверяет действие в коллекции и списке, ошибку и адаптивность на EN/RU/RO и ширинах 320/390/768/1024/1440 px с подменой API.

Браузерная проверка использует изолированную среду на `localhost:5174` и Mailpit, без настоящей отправки писем. Проверяются добавление и удаление реальных тестовых записей, подтверждение/отмена, ошибка и повтор, сохранение после перезагрузки, защита второго аккаунта, доступность и адаптивность EN/RU/RO на 320/390/768/1024/1440 px. Контрольные изображения — `design/preview/wishes-390.png`, `wishes-1440.png`, `new-wish-390.png`, `new-wish-1440.png`; данные на них созданы только в тестовой БД.
