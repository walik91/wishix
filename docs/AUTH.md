# Email-аккаунты Wishix

Текущий объём: регистрация и вход по email с подтверждением и восстановлением пароля, а также вход, регистрация и подключение Google. По решению владельца от 2026-11-18 Facebook исключён из текущих планов; существующая реализация сохраняется. Технические параметры ниже **предлагаются**; продуктовые требования — в [PROJECT.md](PROJECT.md).

## Пользовательский сценарий

1. `/register`: email, username, пароль → письмо на выбранном языке → ввод кода на той же странице. Клиент формирует основу подсказок из локальной части email и запрашивает до четырёх свободных username; ручной ввод не перезаписывается. Подсказки не резервируют username.
2. Подтверждение создаёт аккаунт и сессию, открывает `/my` («Моё»). Email и username занимают только подтверждённые аккаунты.
3. `/login`: email и пароль. Перезагрузка и перезапуск сервера не завершают действующую сессию. Выход отзывает её на сервере.
4. `/forgot-password`: email → код и новый пароль → возврат ко входу. Все предыдущие сессии и коды восстановления аккаунта отзываются.

`/my` пока показывает данные своего аккаунта и выход. Создание желаний/списков — следующий самостоятельный этап.

Пароль: 4–128 символов Unicode; минимум 4 утверждён владельцем 2026-11-04 и применяется при регистрации и восстановлении. Username: 3–30 символов `[a-z0-9_]`, регистр не различается. Email: ASCII-адрес без отображаемого имени, обрезка пробелов и нижний регистр. Код: 6 цифр, 10 минут, 5 неверных попыток. Повторная отправка через 60 секунд заменяет код и восстанавливает попытки. Просроченный challenge можно обновить до 24 часов после его истечения. Сессия: 7 дней, без автоматического продления.

Незавершённый challenge хранится только в памяти страницы. Если страницу обновили, регистрацию/восстановление следует начать снова. Письмо с кодом само по себе не содержит challenge-токена и не является ссылкой входа.

## Настройки

Настройки находятся в корневом `.env`, который исключён из Git. `.env.example` не создаётся по ранее принятому правилу проекта.

| Переменная | Назначение |
|---|---|
| `APP_ORIGIN` | Точный внешний origin без завершающего `/`, например `http://localhost:5173` в разработке. В production — HTTPS-адрес выбранного хоста |
| `AUTH_SECRET` | Случайный секрет минимум 32 символа для HMAC-кодов/лимитов. Не менять при каждом запуске: смена делает выданные коды недействительными |
| `AUTH_TRUSTED_PROXY_CIDRS` | Через запятую только сети доверенных прокси, которые перезаписывают `X-Real-IP`. Пусто — использовать socket IP; пользователи одного прокси делят IP-лимит |
| `SMTP_HOST`, `SMTP_PORT` | SMTP-сервер и порт. В текущем рабочем окружении: `smtp.zoho.eu`, `587` |
| `SMTP_FROM` | Email отправителя. Текущий адрес предоставлен владельцем, отображаемое имя — Wishix |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | SMTP-авторизация; пароль не копировать в документацию/коммиты |
| `SMTP_SECURITY` | `starttls` (587), `tls` (обычно 465), `none` только для локального тестового SMTP |

`APP_ENV` задаётся Compose: development / production. Production отказывается запускаться с HTTP-origin или незашифрованным SMTP. Требуется внешний HTTPS-прокси; выбранного домена в коде нет. Cookie получает `Secure` из настроенного origin, а не из недоверенного клиентского заголовка.

Текущую Docker-подсеть можно проверить командой `docker network inspect wishix_default --format '{{range .IPAM.Config}}{{.Subnet}}{{end}}'`. Доверять ей допустимо только в текущей схеме, где Go-порт не опубликован, сеть контролируется проектом, а фронтенд перезаписывает IP-заголовок. При другом развёртывании указать его реальные доверенные прокси; не доверять произвольным приватным сетям автоматически.

После изменения настроек: `docker compose up -d --build`. Для production — соответствующая команда из README.

## Google

В Google Cloud создайте проект и настройте Google Auth Platform (название, контакт и тип аудитории External). Для тестового режима добавьте нужные Google-аккаунты в Test users. В Clients создайте OAuth-клиент типа Web application. Его разрешённый redirect URI должен в точности совпадать с `APP_ORIGIN` + `/api/auth/google/callback`, например `http://localhost:5173/api/auth/google/callback` при таком локальном origin. Для публичного окружения используется его HTTPS-origin; отдельный клиент или URI для каждого окружения настраивается в Google Cloud.

Добавьте в локальный `.env` значения `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` и пересоздайте сервер через Compose. Секрет не отправляется в браузер, чат или Git. Если обе переменные пусты, вход через Google скрыт; при наличии только одной сервер откажется запускаться. Источник значений — созданный Google OAuth client, а не SMTP или пароль от аккаунта Google.

Новый пользователь выбирает Google и username; отдельное письмо для Google-email не отправляется, но требуется утверждение Google `email_verified`. Существующий пользователь входит своим способом и подключает Google в профиле. Совпадение email не связывает аккаунты автоматически. Вход через уже подключённый Google использует его стабильный `sub`, а не email. Пароль не предусмотрен для аккаунта, созданного через Google; запрос восстановления пароля для него имеет такой же публичный ответ, как для отсутствующего аккаунта, и не отправляет код.

Откат миграции `008_google_auth.sql` удаляет связи Google и лишает Google-only аккаунты способа входа. В рабочей базе не выполнять этот откат без отдельного решения о сохранении данных и восстановлении доступа.

Сервер использует одноразовый state, PKCE и callback, привязанные к браузеру; привязка Google дополнительно требует исходной действующей сессии. Google access token нужен только для серверного UserInfo и не сохраняется. Nginx не записывает callback в access log и исключает параметры callback из своих proxy error logs, Vite редактирует их в сообщении об ошибке прокси. Внешние прокси и сервисы перед приложением также необходимо настроить так, чтобы не записывать query callback. Переход к списку после входа для бронирования использует существующий механизм возврата. Дополнительно о принятых рисках доверия email — [GOOGLE_AUTH_PROPOSAL.md](GOOGLE_AUTH_PROPOSAL.md).

## Facebook

Существующая реализация описана для сопровождения кода и данных. Дальнейшая разработка и запуск Facebook-входа сейчас не планируются; настройки и код в этой задаче не меняются. При наличии полной конфигурации существующий код по-прежнему может включить вход.

В [Meta for Developers](https://developers.facebook.com/) создайте приложение с возможностью Facebook Login и настройте веб-вход. В разрешённые OAuth redirect URI внесите точный `APP_ORIGIN` + `/api/auth/facebook/callback`. Для разработки нужен аккаунт с ролью в приложении; для входа остальных пользователей необходимо выполнить требования Meta и перевести приложение в рабочий режим. Доступ и процесс проверки зависят от настроек приложения Meta.

Meta требует описать в политике конфиденциальности, как запросить удаление пользовательских данных; вариант с [callback удаления](https://developers.facebook.com/docs/development/create-an-app/app-dashboard/data-deletion-callback/) также требует отдельной реализации. Такая обработка запросов и политика в текущем этапе не реализованы и должны быть подготовлены перед публичным запуском.

В `.env` добавьте `FACEBOOK_APP_ID` и `FACEBOOK_APP_SECRET`, затем пересоздайте сервер. Секрет хранится только на сервере, не отправляется в чат и не коммитится. Если хотя бы одна переменная отсутствует, пуста или состоит из пробелов, вход через Facebook отключён: кнопки скрыты, а сервер не принимает начало или завершение Facebook-авторизации. Остальные способы входа продолжают работать. Запрашиваются `public_profile` и `email`, причём предоставление email зависит от Facebook и разрешения пользователя.

При отсутствии email пользователь выбирает username и входит. В профиле ему предлагается добавить адрес для писем; адрес закрепляется только после подтверждения одноразовым кодом и уникален среди аккаунтов. До этого бронирование требует добавить email в профиле. Полученный от Facebook адрес по решению владельца принимается без дополнительного кода, хотя API не предоставляет отдельного подтверждения владения адресом. Совпадающий email не связывает аккаунты: для подключения Facebook необходимо войти в существующий аккаунт. Для подключённой идентичности последующий вход работает и без email от Facebook.

Сервер обменивает authorization code на токен, запрашивает app-scoped ID и email в Graph API и вычисляет `appsecret_proof`; токен не хранится. State одноразовый и проверяется с HttpOnly-cookie, подключение требует ту же действующую сессию. Внешние прокси не должны записывать параметры `/api/auth/facebook/callback`. Откат `009_facebook_auth.sql` удаляет связи Facebook и может лишить доступа Facebook-only аккаунты; если есть аккаунты без email, восстановление NOT NULL остановит откат. Не выполнять откат на рабочей базе без плана сохранения доступа.

## API

Все POST: JSON, заголовки `Origin: <APP_ORIGIN>`, `X-Wishix-Request: 1`, `Content-Type: application/json`. Тела до 4096 байт. Сессия передаётся автоматически cookie, а не Bearer-токеном.

| Метод и путь | Вход | Успех |
|---|---|---|
| `POST /api/auth/register` | `username`, `email`, `password`, `locale` | 202: `challenge`, `resend_after` |
| `POST /api/auth/username-suggestions` | `username`: допустимая основа | 200: до четырёх свободных на момент проверки `suggestions`; не резервирует их |
| `POST /api/auth/verify-email` | `challenge`, `code` | 200: `user`, Set-Cookie |
| `POST /api/auth/resend` | `challenge` | 200: `status`, `resend_after` |
| `POST /api/auth/login` | `email`, `password` | 200: `user`, Set-Cookie |
| `GET /api/auth/me` | Cookie | 200: `user` |
| `POST /api/auth/logout` | `{}` и cookie | 200: `status`, удаление cookie |
| `POST /api/auth/forgot-password` | `email`, `locale` | 202: `challenge`, `resend_after` |
| `POST /api/auth/reset-password` | `challenge`, `code`, `password` | 200: `status`, удаление cookie |
| `GET /api/auth/google/status` | Необязательная cookie | 200: доступность и статус подключения Google для текущего пользователя |
| `POST /api/auth/google/start` | `mode`: `login` или `link`; для `link` — cookie сессии | 200: адрес Google, одноразовая HttpOnly-cookie состояния |
| `GET /api/auth/google/callback` | Ответ Google и cookie состояния | Перенаправление на вход, профиль или выбор username; данные ответа Google не отображаются |
| `POST /api/auth/google/complete` | `username` и HttpOnly-cookie незавершённой регистрации | 200: `user`, cookie сессии |
| `GET /api/auth/facebook/status` | Необязательная cookie | 200: доступность и статус подключения Facebook |
| `POST /api/auth/facebook/start` | `mode`: `login` или `link` | 200: адрес Facebook и cookie состояния |
| `GET /api/auth/facebook/callback` | Ответ Facebook и cookie состояния | Перенаправление на вход, профиль или выбор username |
| `POST /api/auth/facebook/complete` | `username` и cookie незавершённой регистрации | 200: `user`, cookie сессии |
| `POST /api/auth/add-email` | Сессия, `email`, `locale` | 202: challenge для добавления email |
| `POST /api/auth/confirm-added-email` | Сессия, `challenge`, `code` | 200: email привязан к текущему аккаунту |

`user` содержит только `id`, `username`, `email` владельца текущей сессии; при отсутствии адреса `email` — пустая строка. Ответы не кэшируются. Ошибки имеют вид `{"error":"invalid_code"}`; 400 — валидация/код, 401 — неверные данные или сессия, 403 — origin/CSRF, 409 — занятый email/username, 415 — формат, 429 — лимит, 503 — доставка/инфраструктура. Тексты переводит клиент. Для неизвестного email восстановление выдаёт такой же непрозрачный challenge и ответы повторной отправки, но письма не отправляет. Разница времени SMTP пока не скрыта очередью доставки.

Лимиты: 5 отправок кодов на email в час, суммарно регистрация/восстановление/повтор; 15 попыток входа на email за 15 минут; IP — 20 запросов за 15 минут отдельно для регистрации/восстановления/повтора и 100 для остальных auth POST. Проверяются атомарно в БД, переживают перезапуск API. Это защитные параметры auth, не лимиты гостевого бронирования.

Подсказки проверяют существующие аккаунты и действующий реестр прежних username. Запрос ограничен до 100 кандидатов и общим IP-лимитом auth; email серверу подсказок не передаётся. Проверка является предварительной: уникальность окончательно обеспечивается при подтверждении регистрации.

Секреты и SQL-параметры не логируются; cookie-токены отсутствуют в JSON и URL. Коды хранятся как HMAC, пароли как Argon2id, токены как SHA-256. SMTP вызывается после коммита, поэтому повторы CockroachDB не отправляют дубликаты писем. При сетевом сбое после приёма письма возможен неопределённый результат доставки; надёжная очередь пока не реализована.

## Миграции и проверки

SQL-файлы: `server/internal/db/migrations/`. По требованию владельца используется Goose v3.29.0: явные Up/Down, история в `goose_db_version`, автоматический Up перед запуском API. Начальная миграция идемпотентна, поэтому принимает и прежнюю схему без удаления данных. Для следующего изменения добавлять новый номер; уже применённые файлы не редактировать. Консольные команды `up`, `down`, `status`, `version` и правила отката описаны в [MIGRATIONS.md](MIGRATIONS.md). Откат первой миграции удаляет таблицы аккаунтов и их данные; автоматически он не выполняется.

Обычные Go-проверки входят в Docker build: `go vet ./...` и `go test ./...`. Они проверяют криптографию, production-настройки, CSRF/JSON и доверие прокси наряду с существующими тестами жизненного цикла/транзакций.

Интеграционные проверки используют отдельный Compose-проект и только тестовые реквизиты. Рабочий `.env`, реальные SMTP-реквизиты и тома Wishix в тестовые контейнеры не передаются:

```sh
docker compose -f compose.auth-test.yaml run --rm go-tests
```

Проверяются полный жизненный цикл аккаунта, cookie/приватные DTO, невозможность входа до подтверждения, повторное использование кода, лимит попыток, resend/expiry, восстановление и отзыв сессий, гонка входа со сбросом пароля, уникальность email, конкурирующие подтверждения и rate limits, сбои SMTP и очистка. Миграционные тесты проверяют Goose Up → Down → Up, историю версий, повторное применение без потери данных и переход с прежней схемы. Тесты создают случайные схемы `auth_test_*`/`tx_test_*` в тестовой БД и удаляют только их.

Для ручной проверки формы и доставки в локальный ящик:

```sh
docker compose -f compose.auth-test.yaml up -d --build
```

Тестовое приложение: <http://localhost:5174>, Mailpit: <http://localhost:8026>. Письма остаются в Mailpit. Остановка: `docker compose -f compose.auth-test.yaml down` (тома сохраняются). Основное приложение на 5173 продолжает использовать настроенный Zoho SMTP.
