# Email-аккаунты Wishix

Объём поручен владельцем 2026-11-04: рабочая регистрация и вход по email, подтверждение адреса и восстановление пароля. Google/Facebook — позже. Технические параметры ниже **предлагаются** и реализованы для проверки; продуктовые требования — в [PROJECT.md](PROJECT.md).

## Пользовательский сценарий

1. `/register`: username, email, пароль → письмо на выбранном языке → ввод кода на той же странице.
2. Подтверждение создаёт аккаунт и сессию, открывает `/my` («Моё»). Email и username занимают только подтверждённые аккаунты.
3. `/login`: email и пароль. Перезагрузка и перезапуск сервера не завершают действующую сессию. Выход отзывает её на сервере.
4. `/forgot-password`: email → код и новый пароль → возврат ко входу. Все предыдущие сессии и коды восстановления аккаунта отзываются.

`/my` пока показывает данные своего аккаунта и выход. Создание желаний/списков — следующий самостоятельный этап.

Пароль: 4–128 символов Unicode; минимум 4 утверждён владельцем 2026-11-04 и применяется при регистрации и восстановлении. Username: 3–30 символов `[a-z0-9_]`, регистр не различается. Email: ASCII-адрес без отображаемого имени, обрезка пробелов и нижний регистр. Код: 6 цифр, 10 минут, 5 неверных попыток. Повторная отправка через 60 секунд заменяет код и восстанавливает попытки. Просроченный challenge можно обновить до 24 часов после его истечения. Сессия: 7 дней, без автоматического продления.

Незавершённый challenge хранится только в памяти страницы. Если страницу обновили, регистрацию/восстановление следует начать снова. Письмо с кодом само по себе не содержит challenge-токена и не является ссылкой входа.

## Настройки

Настройки находятся в корневом `.env`, который исключён из Git. `.env.example` не создаётся по ранее принятому правилу проекта.

| Переменная | Назначение |
|---|---|
| `APP_ORIGIN` | Точный внешний origin без завершающего `/`, например `http://localhost:5173` в разработке. В production — HTTPS-адрес выбранного хоста |
| `AUTH_SECRET` | Случайный секрет минимум 32 символа для HMAC-кодов/лимитов. Не менять при каждом запуске: смена делает выданные коды недействительными |
| `AUTH_TRUSTED_PROXY_CIDRS` | Через запятую только сети доверенных прокси, которые перезаписывают `X-Real-IP`. Пусто — использовать socket IP; пользователи одного прокси делят IP-лимит |
| `SMTP_HOST`, `SMTP_PORT` | SMTP-сервер и порт. В текущем рабочем окружении: `smtp.zoho.eu`, `587` |
| `SMTP_FROM` | Email отправителя. Текущий адрес предоставлен владельцем, отображаемое имя — Wishix |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | SMTP-авторизация; пароль не копировать в документацию/коммиты |
| `SMTP_SECURITY` | `starttls` (587), `tls` (обычно 465), `none` только для локального тестового SMTP |

`APP_ENV` задаётся Compose: development / production. Production отказывается запускаться с HTTP-origin или незашифрованным SMTP. Требуется внешний HTTPS-прокси; выбранного домена в коде нет. Cookie получает `Secure` из настроенного origin, а не из недоверенного клиентского заголовка.

Текущую Docker-подсеть можно проверить командой `docker network inspect wishix_default --format '{{range .IPAM.Config}}{{.Subnet}}{{end}}'`. Доверять ей допустимо только в текущей схеме, где Go-порт не опубликован, сеть контролируется проектом, а фронтенд перезаписывает IP-заголовок. При другом развёртывании указать его реальные доверенные прокси; не доверять произвольным приватным сетям автоматически.

После изменения настроек: `docker compose up -d --build`. Для production — соответствующая команда из README.

## API

Все POST: JSON, заголовки `Origin: <APP_ORIGIN>`, `X-Wishix-Request: 1`, `Content-Type: application/json`. Тела до 4096 байт. Сессия передаётся автоматически cookie, а не Bearer-токеном.

| Метод и путь | Вход | Успех |
|---|---|---|
| `POST /api/auth/register` | `username`, `email`, `password`, `locale` | 202: `challenge`, `resend_after` |
| `POST /api/auth/verify-email` | `challenge`, `code` | 200: `user`, Set-Cookie |
| `POST /api/auth/resend` | `challenge` | 200: `status`, `resend_after` |
| `POST /api/auth/login` | `email`, `password` | 200: `user`, Set-Cookie |
| `GET /api/auth/me` | Cookie | 200: `user` |
| `POST /api/auth/logout` | `{}` и cookie | 200: `status`, удаление cookie |
| `POST /api/auth/forgot-password` | `email`, `locale` | 202: `challenge`, `resend_after` |
| `POST /api/auth/reset-password` | `challenge`, `code`, `password` | 200: `status`, удаление cookie |

`user` содержит только `id`, `username`, `email` владельца текущей сессии. Ответы не кэшируются. Ошибки имеют вид `{"error":"invalid_code"}`; 400 — валидация/код, 401 — неверные данные или сессия, 403 — origin/CSRF, 409 — занятый email/username, 415 — формат, 429 — лимит, 503 — доставка/инфраструктура. Тексты переводит клиент. Для неизвестного email восстановление выдаёт такой же непрозрачный challenge и ответы повторной отправки, но письма не отправляет. Разница времени SMTP пока не скрыта очередью доставки.

Лимиты: 5 отправок кодов на email в час, суммарно регистрация/восстановление/повтор; 15 попыток входа на email за 15 минут; IP — 20 запросов за 15 минут отдельно для регистрации/восстановления/повтора и 100 для остальных auth POST. Проверяются атомарно в БД, переживают перезапуск API. Это защитные параметры auth, не лимиты гостевого бронирования.

Секреты и SQL-параметры не логируются; cookie-токены отсутствуют в JSON и URL. Коды хранятся как HMAC, пароли как Argon2id, токены как SHA-256. SMTP вызывается после коммита, поэтому повторы CockroachDB не отправляют дубликаты писем. При сетевом сбое после приёма письма возможен неопределённый результат доставки; надёжная очередь пока не реализована.

## Миграции и проверки

SQL-файлы: `server/internal/db/migrations/`. По требованию владельца используется Goose v3.29.0: явные Up/Down, история в `goose_db_version`, автоматический Up перед запуском API. Начальная миграция идемпотентна, поэтому принимает и прежнюю схему без удаления данных. Для следующего изменения добавлять новый номер; уже применённые файлы не редактировать. Консольные команды `up`, `down`, `status`, `version` и правила отката описаны в [MIGRATIONS.md](MIGRATIONS.md). Откат первой миграции удаляет таблицы аккаунтов и их данные; автоматически он не выполняется.

Обычные Go-проверки входят в Docker build: `go vet ./...` и `go test ./...`. Они проверяют криптографию, production-настройки, CSRF/JSON и доверие прокси наряду с существующими тестами жизненного цикла/транзакций.

Интеграционные проверки используют отдельный Compose-проект и только тестовые реквизиты. Рабочий `.env`, реальные SMTP-реквизиты и тома Wishix в тестовые контейнеры не передаются:

```sh
docker compose -f compose.auth-test.yaml run --rm go-tests
```

Проверяются полный жизненный цикл аккаунта, cookie/приватные DTO, невозможность входа до подтверждения, повторное использование кода, лимит попыток, resend/expiry, восстановление и отзыв сессий, гонка входа со сбросом пароля, уникальность email, конкурирующие подтверждения и rate limits, сбои SMTP и очистка. Миграционные тесты проверяют Goose Up → Down → Up, историю версий, повторное применение без потери данных и переход с прежней схемы. Тесты создают случайные схемы `auth_test_*`/`tx_test_*` в тестовой БД и удаляют только их.

Для ручной проверки формы и доставки в локальный ящик:

```sh
docker compose -f compose.auth-test.yaml up -d --build
```

Тестовое приложение: <http://localhost:5174>, Mailpit: <http://localhost:8026>. Письма остаются в Mailpit. Остановка: `docker compose -f compose.auth-test.yaml down` (тома сохраняются). Основное приложение на 5173 продолжает использовать настроенный Zoho SMTP.
