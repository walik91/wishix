# Wishix — архитектура (рабочий документ)

**Статус:** утверждены Go 1.27.3 + Fx, Vue, GORM, CockroachDB, Goose и запуск через Docker; схема данных и остальные решения уточняются.
**Назначение:** заполнять вместе с Codex по мере выбора архитектуры. Не воспринимать открытые вопросы и предложения ниже как утверждённый стек.

**Актуализация интерфейса, 2026-11-04:** `/my` — обзор с независимой загрузкой списков и желаний через существующие composables; `/my/wishes` — прежняя коллекция с управлением желаниями. Оба маршрута защищены проверкой сессии. Создание желания возвращает к коллекции или в исходный список; на общей главной ссылка на желания ведёт в коллекцию. Описания прежних этапов ниже сохраняют исторический контекст.

На `/my` приветственный блок использует состояния `useWishes` и `useLists`. После успешной загрузки пустой коллекции желаний он предлагает добавить желание, независимо от состояния списков. Если желания есть, блок предлагает создать список только после успешной загрузки пустого массива списков. Пока желания загружаются или при ошибке их загрузки блок скрыт: без этого нельзя выбрать действие.

**Ссылки на списки:** публичный адрес — `/u/{username}/wishlist/{id}`, ссылочный — `/u/{username}/wishlist/{id}/{token}`. Сервер проверяет ID, видимость и при необходимости токен, выдаёт HTTP 301 на актуальный username; переход с токенизированного адреса на публичный — временный HTTP 302. Публичная страница не возвращает токен. Старый формат перенаправляется на соответствующий новый адрес при действующем доступе. Vite реализует тот же маршрут для разработки; Nginx применяет `X-Accel-Redirect`. Ссылочные и недействительные адреса получают `X-Robots-Tag: noindex` до загрузки приложения. Подробности и риск внешних логов — в [LISTS.md](LISTS.md).

## 1. Принятые технические решения

Системные имена проекта: Go-модуль `wishix/server`, npm-пакет `wishix-front`, идентификатор API `wishix-api`, Compose-проект, БД и пользователь приложения `wishix`. Данные хранятся в томе `wishix_db-data`; прежние тома сертификатов сохраняются. Фронтенд использует пространство имён токенов `--wx-*` и SVG из дизайн-документации; favicon собирается Vite из того же набора.

2026-11-03 владелец проекта утвердил начало реализации: Go API в `server/`, Vue-фронтенд в `front/`, весь локальный запуск через Docker. Это первый технический этап с текстовой заглушкой и проверкой связи, без продуктовой логики и хранения данных.

### Минимальная реализация первого этапа

Для стартового каркаса **предлагается** и используется простая реализация; эти детали не фиксируют окончательную архитектуру MVP:

- Go 1.27.3 закреплён в `go.mod` и Docker-образе. HTTP остаётся на стандартной библиотеке `net/http`; Fx собирает зависимости и управляет запуском и остановкой. `GET /api/health` возвращает `{"status":"ok","service":"wishix-api"}`. Неизвестные пути получают 404, неподдерживаемые методы — 405.
- Vue 3, JavaScript и Vite, Node.js 24 в Docker. Прямые зависимости закреплены в `package.json`, транзитивные — в `package-lock.json`; установка через `npm ci`.
- Отдельные словари `en`, `ru`, `ro`, базовый язык `en`. Тексты заглушки вынесены из компонентов; язык документа обновляется при переключении.
- Браузер обращается к единому адресу приложения: все пути с префиксом `/api` проксируются на `http://server:8080` внутри сети Compose, остальные запросы обрабатывает фронтенд. В разработке прокси работает через Vite, в production — через Nginx. Проверка API доступна по `/api/health` на том же внешнем порту, что и страница. Адрес контейнера не используется браузером, отдельная настройка CORS не нужна.
- Go собирается в отдельном Docker-этапе, исполняемый контейнер работает без root. Для разработки фронтенд использует Docker-этап `development` с Vite от пользователя `node`.
- Общий внешний порт задаётся обязательным `APP_PORT` в рабочем корневом `.env`, отдельного `.env.example` нет. В разработке он привязан только к `127.0.0.1`; в production доступен на сетевых интерфейсах сервера. В обоих случаях Go слушает `8080` только внутри сети Docker. Healthchecks проверяют оба сервиса; фронтенд стартует после готовности API. После изменения `.env` повторить команду запуска соответствующего режима из `README.md`.
- Исходники страницы подключены к контейнеру только для чтения, изменения подхватываются Vite. `docker compose up --build --watch` дополнительно пересобирает Go при изменениях; обычный запуск описан в `README.md`.

### Минимальный запуск на сервере

`docker compose -f compose.prod.yaml up -d --build` собирает и запускает приложение без watch и монтирования исходников. Для реализации **предлагается** и используется Docker-этап `production`: Vite собирает Vue в `dist`, затем файлы обслуживает Nginx 1.30 из образа `nginx/nginx-unprivileged`, без Node.js в исполняемом контейнере. Nginx направляет `/api*` в Go и возвращает `index.html` для маршрутов Vue. DNS-адрес Go-контейнера обновляется через встроенный DNS Docker; замена контейнера не требует ручной правки прокси. Nginx перезаписывает переданные клиентом IP-заголовки; правила доверенных прокси и IP-лимитов на Go-сервере ещё предстоит согласовать до реализации бронирований.

Оба сервиса имеют `restart: unless-stopped`, поэтому запускаются повторно при перезапуске Docker. Та же команда применяет обновления кода и `.env`. Production теперь требует HTTPS в `APP_ORIGIN` для защищённой cookie; внешний HTTPS-прокси, хостинг и домен настраиваются отдельно. Внутренний HTTP между прокси и приложением сохраняется. Конкретный хостинг, домены, CI/CD и мониторинг пока не выбраны.

По запросу владельца текущий ПК подключается через Cloudflare Tunnel для тестирования режима разработки. Порт привязан к `127.0.0.1`, внешний адрес и токен задаются только в исключённом из Git `.env`. Контейнер `cloudflared` запускается с Compose после готовности фронтенда, разделяет его сетевое пространство и использует внутренний порт Vite; маршрут управляется в Cloudflare. Vite разрешает hostname из `APP_ORIGIN` и перезаписывает IP-заголовок; поэтому посетители туннеля делят IP-лимиты. Это ограничение текущей настройки, а не определение личности посетителей. Домен тестирования не фиксирует будущий домен проекта.

Критерий готовности первого этапа выполнен: команды разработки и production запускают соответствующие режимы, страница и Go API доступны через один внешний порт, CockroachDB подключена. Реализованы email-аккаунты, сессии, управление желаниями и списками, гостевые ссылки, публичный профиль и бронирование. Подробности — [LISTS.md](LISTS.md) и [RESERVATIONS.md](RESERVATIONS.md).

### Структура сервера и выбранная БД

```text
server/
  main.go                    # Запуск приложения Fx
  internal/
    app/                     # Сборка графа зависимостей Fx
    controllers/             # HTTP, валидация входа, коды ответов и DTO
    services/                # Бизнес-правила и границы транзакций
    repositories/            # Чтение и запись через GORM
    models/                  # Модели таблиц БД
    db/                      # Подключение GORM, пул и жизненный цикл БД
    infrastructure/          # HTTP-сервер и маршрутизация
```

Сервисы не должны принимать `http.Request`, отдавать HTTP-ответы или строить GORM-запросы. Контроллеры вызывают сервисы, сервисы — репозитории; интерфейсы репозиториев вводятся по нуждам конкретного сервиса. HTTP DTO отделены от моделей таблиц, чтобы случайно не возвращать приватные поля. Первый сценарий хранения добавил модели User/AuthChallenge/AuthSession и предметный Auth-репозиторий. Инфраструктурные параметры и криптографические функции находятся в `internal/auth/`, SQL-миграции — в `internal/db/migrations/`.

`/api/health` проходит через контроллер и сервис и проверяет работоспособность самого API, независимо от последующих сбоев БД. `/api/ready` дополнительно выполняет `PingContext` с тайм-аутом 2 секунды: отвечает 200 при доступной БД и обобщённым 503 без внутренних ошибок и параметров подключения при сбое. Страница проверяет `/api/ready`; healthchecks API и production-прокси тоже используют его. Для технической проверки готовности не создаётся искусственный репозиторий: сервис использует метод проверки общего `sql.DB`-пула.

До открытия HTTP-порта Fx выполняет проверку соединения с БД и явные SQL-миграции; ошибка прерывает запуск. HTTP-порт открывается синхронно в `fx.Lifecycle.OnStart`; ошибка привязки порта также прерывает запуск. `OnStop` останавливает очистку истёкших auth-записей, корректно завершает HTTP-запросы, затем закрывает пул БД. Ошибка работающего HTTP-сервера запрашивает остановку Fx с ненулевым кодом.

Утверждены CockroachDB и GORM. GORM работает с CockroachDB через `gorm.io/driver/postgres`. Фабрика `db.New` зарегистрирована в Fx и создаётся при запуске приложения. Параметры `DB_NAME`, `DB_USER` передаются из корневого `.env` через Compose. По указанию владельца используется `sslmode=disable`; пароль базой не проверяется. Тайм-аут подключения — 5 секунд. Пул ограничен 10 открытыми и 5 простаивающими соединениями; проверяется в `OnStart` и закрывается в `OnStop`, а при ошибке первоначальной проверки закрывается сразу. Строка подключения и SQL-параметры не логируются, `AutoMigrate` при старте не запускается.

### Структура фронтенда

**Статус: предлагается; минимальное разделение применено к стартовой странице.** Цель — менять оформление преимущественно в стилях и компонентах, сохраняя запросы к серверу и поведение сценариев. Полностью независимую замену любого интерфейса не обещаем: изменение самого пользовательского сценария может потребовать изменения логики.

Текущая структура `front/src/`:

```text
src/
  main.js                         # Запуск Vue и подключение базовых стилей
  App.vue                         # Временный выбор страницы по URL, алиасы и экран 404
  assets/brand/                   # Копии используемых ресурсов из docs/design/assets/
  components/ui/                  # Кнопки, поля, иконки, карточка, badge, empty state, skeleton, dialog/sheet и аватар
  components/auth/                # Общие PasswordField и SocialAuthButtons
  components/navigation/          # PublicHeader гостевых страниц и адаптивная AppNavigation владельца
  components/wishes/              # WishCard для реальных желаний; ListCard пока визуальный шаблон
  layouts/PublicLayout.vue        # Единые контейнер, шапка, main и подвал гостевых страниц
  layouts/AppShell.vue            # Оболочка «Моё», навигация, данные аккаунта и выход
  layouts/AuthLayout.vue          # Фирменная панель и форма входа/регистрации внутри PublicLayout
  api/
    client.js                     # Общий HTTP-транспорт для JSON-ответов
    system.js                     # Проверка готовности сервера
  composables/
    useServerConnection.js        # Состояние проверки связи и повторная проверка
  pages/
    GuestHomePage.vue              # Гостевая главная: описание, шаги, FAQ и ссылки на формы
    StartPage.vue                  # Техническая проверка соединения, /status
    LoginPage.vue                 # Вход по email и паролю
    RegisterPage.vue              # Регистрация и подтверждение email кодом
    RecoveryPage.vue              # Восстановление пароля кодом
    MyPage.vue                    # Реальная коллекция желаний и удаление с подтверждением
    NewWishPage.vue               # Ручное добавление желания на отдельной странице
  styles/
    base.css                      # Базовые глобальные стили
    tokens.css                    # Точная копия docs/design/tokens.css
  i18n.js                         # Выбор языка и получение переводов
  locales/
    en.json
    ru.json
    ro.json
```

Границы ответственности:

- **`api/` — взаимодействие с сервером.** Только здесь находятся `fetch`, пути запросов и работа с форматом ответа. `client.js` добавляет `/api`, задаёт тайм-аут по умолчанию 5 секунд, проверяет HTTP-статус и читает JSON; при HTTP-ошибке сохраняет числовой `error.status`. Он не показывает уведомления, не переводит тексты, не хранит состояние Vue и не логирует запросы или секреты. Сейчас нужен только запрос с JSON-ответом; обработку других форматов добавляем вместе с реальным сценарием. `system.js` знает контракт `/ready` и возвращает понятный вызывающему коду результат. Будущие запросы группируем по предмету: `wishes.js`, `wishlists.js`, `reservations.js`, когда появится соответствующий API. Отдельный файл для каждого запроса не нужен.
- **`composables/` — состояние и поведение сценария во Vue.** Например, `useServerConnection` запускает проверку, хранит `checking / connected / unavailable`, обрабатывает сбой и даёт действие для повторной проверки. Он вызывает функции `api/`, не знает URL, JSON-полей сервера, разметки и CSS. Простое локальное состояние вроде открытого меню можно оставить в компоненте. Composable выделяем, когда поведение самостоятельно, переиспользуется или мешает читать разметку; обязательного файла на каждый компонент нет.
- **`pages/` — сборка экрана.** Страница соединяет состояние сценария, действия и визуальные компоненты, показывает loading/empty/error и переведённые сообщения. В ней нет прямых сетевых запросов. **Предлагается** сохранить выбор страницы по URL и обычные переходы браузера: `/`, `/register`, `/login`, `/forgot-password`, `/my`, `/my/wishes/new`, `/status`. Алиасы `/sign-up` и `/sign-in` заменяют URL на `/register` и `/login`, сохраняя query/hash. `useSession` проверяет `/api/auth/me`: без сессии `/my` и `/my/wishes/new` переводят ко входу, при сбое связи показывают повторную проверку. Авторизованные посетители `/login` и `/register` переходят в `/my`; общая главная `/` остаётся доступной всем. Проверки на фронтенде служат навигации; доступ к данным всегда проверяет сервер. Неизвестный путь показывает локальный экран 404; HTTP-статус остаётся ответом SPA-сервера. Отдельная библиотека маршрутизации этому небольшому сценарию пока не требуется.
- **Стили — рядом с тем, что они оформляют.** В `styles/base.css` остаются общие правила документа; стили страницы или компонента находятся в его `<style scoped>`. Продуктовый интерфейс использует токены из `docs/design/tokens.css` или их точный эквивалент, а ресурсы — из `docs/design/assets/`, согласно `DESIGN_SYSTEM.md`. Макет входа использует точную копию токенов в `src/styles/tokens.css` и копии выбранных SVG в `src/assets/brand/`, чтобы сборка Docker не зависела от файлов за пределами `front/`. При обновлении оригиналов эти копии нужно синхронизировать. Стартовая техническая заглушка сохраняет собственные локальные стили; они не являются новым эталоном.
- **`i18n.js` и `locales/` — локализация.** Текст интерфейса не попадает в API-модули и не вшивается в разметку; базовый язык и резервный перевод — `en`, также поддерживаются `ru` и `ro`. По запросу владельца язык при загрузке выбирается в порядке: поддерживаемое значение cookie `wishix_locale` → первый поддерживаемый язык из `navigator.languages` (с резервным `navigator.language`) → `en`. Региональная часть кода браузера отбрасывается. Ручное переключение сохраняется синхронно в cookie на один год, с `Path=/`, `SameSite=Lax` и `Secure` на HTTPS; домен не задаётся. Автоматически определённый язык не записывается: до ручного выбора новые посещения продолжают учитывать браузер. Неподдерживаемые/повреждённые cookie игнорируются; при запрете cookies интерфейс продолжает работать с выбором языка на текущей странице. Атрибут `html.lang` и заголовок документа обновляются при переключении.

Направление зависимостей: **страница → composable → API-модуль → HTTP-клиент**. Визуальные компоненты получают данные через props и сообщают о действиях через события; они не выполняют запросы. API-модули не импортируют страницы или Vue. Простое действие без отдельного состояния допустимо связать с API прямо в `<script setup>` страницы через импорт API-функции; дополнительные обёртки ради соблюдения цепочки не нужны.

Как развивать структуру без лишних слоёв:

1. При появлении повторяемого интерфейса добавляем `components/ui/` для Button, Input, Surface, Dialog и других общих элементов. Предметные компоненты располагаем, например, в `components/wishes/WishCard.vue` и `components/wishlists/ListCard.vue`. Компонент, используемый один раз, также можно выделить, если это заметно упрощает большой экран.
2. Повторяемую оболочку и навигацию выделяем в `layouts/AppShell.vue` и компоненты навигации. Mobile и desktop используют одни данные и действия; различается адаптивная компоновка. Создание/редактирование желания остаётся отдельной страницей по `PROJECT.md`.
3. Небольшие чистые вычисления сначала держим рядом со сценарием. Отдельный предметный модуль нужен, если вычисление переиспользуется или требует самостоятельной проверки. Не создаём заранее фронтенд-слои repositories/services, универсальные CRUD-классы, DI или дублирующие сервер модели.
4. Состояние начинаем хранить локально. Общий store, кэш серверных данных и новые библиотеки выбираем при конкретной потребности нескольких экранов, а не для этой структуры каталогов. Не создаём пустые папки под будущие функции и не дробим файлы ради условного ограничения строк.

Пример границ изменений: оформление кнопки меняется в её компоненте и токенах; расположение карточек — в странице или layout; URL и формат ответа — в `api/`; поведение отправки формы и её состояния — в соответствующем composable. При сохранении тех же данных и действий визуальные изменения не должны требовать правки API или логики сценария.

Критичные правила продукта остаются на сервере: права, лимиты, сроки и атомарность броней. Фронтенд отображает разрешённое представление данных; закрытые сведения о бронях не должны приходить владельцу или другим дарителям с расчётом на скрытие средствами CSS. При выделении логики проверяем поведение сценария и обработку ошибок; при изменении оформления — также адаптивность и доступность по дизайн-документам.

### Управление желаниями — этап 2026-11-04

**Утверждённый объём:** общая коллекция, ручное добавление и удаление без списков. Goose `002_wishes.sql` добавляет `wishes` и упорядоченные `wish_shop_links`. Каждое желание принадлежит аккаунту напрямую, без искусственного системного списка. Создание со ссылками атомарно через существующий Transactor; удаление проверяет владельца в самом SQL-запросе, связанные ссылки удаляет внешний ключ. Цена хранится как `DECIMAL(12,2)` и передаётся строкой.

`GET/POST /api/wishes` и `DELETE /api/wishes/{id}` используют текущую серверную сессию. Владелец не принимается из тела запроса. Приватные DTO, `no-store`, проверка Origin/JSON/custom header и ограничение тела предотвращают раскрытие лишних полей и запросы с чужого сайта. Чужое и отсутствующее желание одинаково отвечают 404. Сервер не загружает магазинные URL.

Vue использует AppShell и защищённые сессией страницы создания и редактирования желания. API находится в `api/wishes.js`; форма редактирования загружает авторизованный GET и отправляет PUT с версией редактируемых полей. В retry-транзакции сервер проверяет эту версию и атомарно заменяет поля и упорядоченные ссылки, не затрагивая изображение, списки и брони. Изменение ссылки при редактировании не вызывает импорт. Подробности и ограничения — в [WISHES.md](WISHES.md). Отметка «Получено» остаётся отдельным этапом.

### Email-аутентификация — текущий этап

**Статус: реализация поручена владельцем; технические решения ниже предлагаются и используются до отдельного уточнения.** Контракты, параметры и команды проверок описаны в [AUTH.md](AUTH.md).

- `001_email_auth.sql` создаёт `users`, `auth_challenges`, `auth_sessions`, `auth_rate_limits`. По прямому указанию владельца миграции переведены на `github.com/pressly/goose/v3` (v3.29.0): аннотации Up/Down, история `goose_db_version`, автоматический `Up` перед открытием HTTP-порта и отдельная команда `server/cmd/migrate` в том же Docker-образе. Goose получает общий `sql.DB` и PostgreSQL-диалект, без глобального состояния. `NO TRANSACTION` оставляет DDL CockroachDB отдельными операторами. Старый исполнитель и проверки SHA-256 удалены; историческая `schema_migrations`, если есть, сохраняется без использования. Начальный Up идемпотентен и принимает существующие таблицы без удаления аккаунтов. Down запускается только явной командой. Подробнее — [MIGRATIONS.md](MIGRATIONS.md).
- Регистрация хранит временный challenge, а подтверждение атомарно создаёт пользователя, удаляет challenge и выдаёт сессию. Email/username уникальны в БД; конкурирующие подтверждения и повторное использование кодов проверяются в SERIALIZABLE-транзакциях с уже существующим retry-менеджером. Неверные попытки фиксируются коммитом, а не теряются при rollback.
- Пароли: Argon2id, индивидуальная соль, параметры OWASP `m=19456 KiB, t=2, p=1`. Коды: HMAC-SHA256 с `AUTH_SECRET` и привязкой к purpose/challenge. Непрозрачные 256-битные токены сессии и challenge хранятся в БД только как SHA-256. Сессия не возвращается в JSON; cookie — HttpOnly, SameSite=Lax, host-only, Path=/, Secure при HTTPS.
- Сброс пароля удаляет все сессии и reset-challenges пользователя в одной транзакции. Выдача сессии при входе блокирует строку пользователя и повторно проверяет хеш, поэтому пароль, проверенный до конкурентного сброса, не выдаёт сессию после него.
- Auth POST требует точный `Origin == APP_ORIGIN`, JSON и `X-Wishix-Request: 1`; тела ограничены 4096 байтами. CORS не включён. Приватный `/api/auth/me` возвращает только id, username, email текущего пользователя с `Cache-Control: no-store`; GET не меняет cookie, чтобы отложенный ответ проверки сессии не стирал новый вход.
- Счётчики запросов атомарны и общие для экземпляров сервера в БД. IP и email в ключах лимитов HMAC-хешированы. По умолчанию сервер использует socket IP. `X-Real-IP` принимается только от явно настроенных `AUTH_TRUSTED_PROXY_CIDRS`; Vite/Nginx перезаписывают заголовок, `X-Forwarded-For` не используется. Без настройки доверия посетители одного прокси делят его IP-лимит. Это auth-ограничения, не реализация правил гостевых броней.
- SMTP работает вне retry-транзакций, с проверкой TLS и тайм-аутом 5 секунд. Zoho настроен через закрытый рабочий `.env`; его STARTTLS и авторизация проверены без отправки реального письма. В тестовой копии используется Mailpit. Если SMTP не принял письмо, API возвращает общую ошибку доставки; аккаунт не создаётся. Очередь гарантированной доставки пока не реализована, поэтому после сетевого сбоя может понадобиться повторный запрос кода.
- Очистка истёкших сессий/счётчиков и старых challenges запускается при старте и каждый час. Письма, пароли, SQL-параметры и токены не логируются. Для восстановления ответы имеют одинаковый контракт и на отсутствующем аккаунте; это не обещание защиты от анализа времени ответа SMTP.

Источники: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [Go Argon2](https://pkg.go.dev/golang.org/x/crypto/argon2), [Zoho SMTP](https://www.zoho.com/mail/help/zoho-smtp.html).

### CockroachDB в Docker

По выбору владельца БД запускается вместе с приложением и в разработке, и в production. Общий `compose.db.yaml` включается в оба Compose-файла; команды запуска не меняются. Для текущего этапа **предлагается** и используется один узел CockroachDB `v26.2.10`; версия образа задана в `.env` через `COCKROACH_IMAGE`. Этот режим не обеспечивает отказоустойчивость при потере узла или сервера; резервное копирование и дальнейшая кластеризация остаются отдельными задачами.

По указанию владельца CockroachDB запускается с `--insecure`: TLS и проверка паролей отключены, включая вход как `root`. Любой клиент с доступом к локальному порту хоста или сети Docker может войти от имени любого пользователя. Данные остаются в постоянном томе; прежние тома сертификатов не удаляются. Сервис `db-init` идемпотентно создаёт БД и пользователя из `.env` и выдаёт ему права на БД приложения и схему `public`; SQL-идентификаторы экранируются в init-скрипте.

В обоих режимах общий `compose.db.yaml` публикует SQL-порт только на `127.0.0.1:26257` хоста для DBeaver; удалённое подключение возможно через SSH-туннель. DB Console не публикуется. База доступна контейнерам по `db:26257`; приложение запускается после успешного `db-init`. Обычный `docker compose down` сохраняет тома. Изменение имени БД или пользователя создаёт новые сущности и не удаляет прежние данные; изменения `.env` применяются повторением команды запуска. Init-скрипт создаёт только БД, пользователя и права; продуктовые таблицы создаёт мигратор API до открытия HTTP-порта.

Источники: [образ CockroachDB v26.2.10](https://www.cockroachlabs.com/docs/releases/v26.2#v26210), [инициализация официального образа](https://github.com/cockroachdb/cockroach/blob/master/build/deploy/cockroach.sh), [Compose include](https://docs.docker.com/compose/how-tos/multiple-compose-files/include/).

GORM упрощает доступ к разным SQL-БД, но не делает миграции, ограничения и поведение транзакций полностью взаимозаменяемыми. Бронирования используют повторы CockroachDB, ограничение уникальности и проверки конкурентных запросов; Fx/GORM сами по себе не обеспечивают атомарность или соблюдение лимитов.

Механизм транзакций реализован отдельно от CRUD: сервис вызывает интерфейс `services.Transactor.WithTransaction(ctx, func(txCtx context.Context) error)`, а прикладные репозитории встраивают общий `repositories.Base`, инициализированный через `NewBase(executor)`, и начинают запросы с `r.Ctx(txCtx)`. Базовый метод возвращает `*gorm.DB`-сессию через `db.Executor.DB(ctx)`; конкретные запросы остаются в предметных репозиториях. Транзакция передаётся приватным типизированным ключом контекста; GORM не попадает в контракт сервиса. Fx предоставляет общий неизменяемый Executor и менеджер. Вложенные вызовы присоединяются к текущей транзакции, ошибки вложенных callback предотвращают commit всей попытки. Чужой или завершённый контекст не может переключить запрос на общий пул. Используется официальный CockroachDB retry-адаптер с ограниченными повторами; подробности, контракт и команды проверок — в [TRANSACTIONS.md](TRANSACTIONS.md).

Источники: [Go](https://go.dev/dl/), [жизненный цикл Fx](https://uber-go.github.io/fx/get-started/http-server.html), [GORM и CockroachDB](https://www.cockroachlabs.com/docs/stable/build-a-go-app-with-cockroachdb-gorm), [повторы транзакций CockroachDB](https://www.cockroachlabs.com/docs/stable/transaction-retry-error-reference).

## 2. Логические модули (концептуально)

- **Identity / Auth** — аккаунт, подтверждение email кодом, пароль, Google, восстановление доступа. Код Facebook сохранён вне текущих планов.
- **Profiles / Social** — профиль, поиск людей, username и redirect-история, подписки, блокировки и жалобы.
- **Wishlists** — списки, режимы доступа, ссылки доступа, копирование и удаление.
- **Wishes** — единая коллекция желаний, связи со списками, полученные подарки, изображения.
- **Shop Links** — несколько ссылок на магазины на одно желание, первичное автозаполнение по первой.
- **Reservations** — атомарные брони на желание, срок, продление, отмена, подтверждение покупки, лимит гостевых броней.
- **Notifications (позже по мере необходимости)** — письма и системные сообщения.

Это **границы ответственности**, а не требование делать отдельные микросервисы. Начинать можно с простого монолита.

## 3. Принципиальные инварианты схемы данных

1. `User 1 — N Wish`.
2. `User 1 — N Wishlist`.
3. `Wish N — M Wishlist` через связь членства; удаление связи не равно удалению желания.
4. `Wish 1 — N ShopLink` (упорядоченные ссылки; первая — первичный источник импорта).
5. Бронирование ссылается на **Wish**, а не только на пару «список — желание»; одновременно может быть только одна действующая бронь (или купленный статус) на одно желание.
6. Контекстом лимита является список, через который создана бронь. Одно и то же желание остаётся занятым во всех списках. Общая коллекция информативна и бронирований не поддерживает.
7. Получение подарка — состояние связи `Wish` с конкретным `Wishlist`.
8. Публичный статус брони — производный, без раскрытия внутреннего `purchased`.

Реализованные списки хранятся в `wishlists` и `wishlist_wishes` (Goose 004). Отметка получения хранится в связи желания со списком (Goose 010). Её установка и завершение брони исходного списка выполняются в одной транзакции. CRUD и членство проходят контроллеры → services.Lists → repositories.Lists. Гостевая страница передаёт ID и, для режима «по ссылке», токен в URL и JSON-теле фиксированного POST; изображения читаются с повторной проверкой видимости, токена и членства. Токен сохраняется при смене режима и меняется только по подтверждённому действию владельца. Общая коллекция не является строкой wishlists и не публикуется обычными настройками списка. Существующий `users.show_all_wishes` управляется отдельным авторизованным API; гостевые данные и изображения проверяют флажок на сервере. Коллекция использует те же гостевые карточки желаний без действий бронирования и без статусов. Детали — [LISTS.md](LISTS.md).

Goose 011 добавляет отображаемое имя и отдельный флажок публичности. Авторизованный поиск выбирает только username и разрешённое имя; условие публичности применяется и к сопоставлению, и к возвращаемым данным. Страницы выдачи ограничены и используют курсор username. Приватная настройка и публичный профиль используют отдельные DTO. Параметры и проверки — [SEARCH.md](SEARCH.md).

Бронирование использует Goose 005–007, контроллеры, сервис и репозиторий `Reservations`. Код подтверждения хранится как HMAC, токен управления воспроизводимо выводится из ID брони и `AUTH_SECRET` и проверяется по хешу. После проверки гостевого кода сервер в той же транзакции проверяет наличие подтверждённого аккаунта и, если он есть, требует вход вместо создания гостевой брони; код не выдаёт сессию. Доступ и лимиты проверяются в сериализуемой транзакции; первичный ключ по желанию предотвращает дублирование. Очередь писем фиксируется в той же транзакции, а отправка и повторы происходят вне неё. Сроки используют сохранённый часовой пояс списка. Контракт, ограничения и тесты — [RESERVATIONS.md](RESERVATIONS.md).

## 4. Нефункциональные требования

- Mobile-first, доступность, локализация `en/ru/ro`.
- Серверная авторизация доступа и недоступность чужих приватных данных.
- Атомарность бронирований и корректные конкурентные запросы.
- Секретные токены управления, безопасное хранение паролей и email-кодов, rate limits для аутентификации.
- Безопасное получение страниц магазинов (SSRF/редиректы/таймауты/ограничения размеров, обработка недоверенного HTML).
- Поддержка разных валют без автоматической конвертации в MVP.
- Миграции, тесты бизнес-логики и воспроизводимый локальный запуск.

## 5. Последовательность реализации

1. Начальный каркас по запросу владельца: `server/` + `front/`, текстовая страница, проверка Go API, локальный запуск в Docker.
2. CockroachDB с GORM подключена. Первый сценарий хранения — email-регистрация, подтверждение, вход/выход и восстановление; предложенные миграции, сессии и параметры зафиксированы в AUTH.md. **Не считать остальные невыбранные части стека утверждёнными.**
3. Развивать проект небольшими вертикальными этапами с интерфейсом, API, хранением и релевантными проверками; каждый этап имеет свои границы и критерии готовности.
4. Реализовать согласованные сроки и лимиты бронирований, атомарность и защиту секретных ссылок. Сохранение даты и уведомлений должно быть согласовано с повторами транзакций CockroachDB; принятые технические решения фиксировать здесь.
