# План подготовки Wishix к production

**Статус:** план обсуждён с владельцем 2026-11-19; скрипт ручной копии и восстановления БД подготовлен 2026-11-20. Скрипт обновления и production-сервер ещё не подготовлены. Документ фиксирует договорённости и предложения для следующих этапов.

## Договорённости

- Приложение планируется разместить на одном сервере Hetzner с Docker и Docker Compose. Допустим короткий перерыв при обновлении. Отказоустойчивый кластер пока не планируется.
- Домен и внешний доступ — через Cloudflare. HTTPS и настройки Cloudflare владелец настраивает самостоятельно; конкретный домен не закреплять в проекте. Владелец рассматривает режим Flexible: браузер соединяется с Cloudflare по HTTPS, а Cloudflare с сервером — по HTTP. На последнем участке данные, включая учётные данные и cookie, не шифруются. При реализации не предполагать наличие HTTPS между Cloudflare и сервером.
- CockroachDB остаётся в текущем режиме `--insecure`. Изображения желаний и аватары остаются в базе, отдельное S3-хранилище сейчас не требуется.
- Исходники размещаются в Git-репозитории владельца, для production используется ветка `main`. Адрес репозитория и способ доступа сервера уточнить при настройке. Не настраивать удалённый репозиторий самостоятельно без отдельной команды владельца.
- Владелец отправляет изменения в Git, подключается к серверу по SSH и вручную запускает один скрипт обновления. Автоматический деплой и платные сервисы автоматизации пока не требуются.
- Автоматические и внешние резервные копии пока не настраиваются. Нужен ручной скрипт полной копии БД, чтобы скачать её на ПК, восстановить для локального тестирования и при необходимости использовать как резервную копию. Частоту ручного копирования определяет владелец.
- Сложный автоматический откат не обязателен. Запоминание предыдущей версии и безопасный вариант отката необходимо проработать; опасные откаты схемы не выполнять автоматически.

## Что уже есть

- `compose.prod.yaml` собирает и запускает frontend и API, а через `compose.db.yaml` — CockroachDB на одном узле. Контейнеры настроены на перезапуск вместе с Docker.
- Данные CockroachDB находятся в именованном томе `wishix_db-data`. Обычные перезапуски, пересоздание контейнера и `docker compose down` сохраняют том. Это не защищает от потери диска, удаления тома или повреждения данных; `docker compose down -v` удаляет тома проекта.
- Изображения желаний (`wish_images`) и аватары (`profile_avatars`) хранятся в БД. Полная копия должна включать их вместе с таблицами приложения и историей миграций.
- API автоматически запускает Goose `up` при старте. Для ручного управления существуют `migrate version`, `status`, `down` и `down-to VERSION`; `down` откатывает одну миграцию. Подробности и ограничения — [MIGRATIONS.md](MIGRATIONS.md).
- Ручной скрипт полной копии и восстановления реализован; команды и ограничения — [DATABASE_BACKUP.md](DATABASE_BACKUP.md). Скрипт обновления пока отсутствует; текущее состояние запуска описано в [README.md](../README.md).

## Предлагаемый план реализации

### 1. Подготовка сервера

1. Уточнить адрес репозитория, способ доступа к нему, параметры сервера и расположение проекта. Подготовить production `.env` вне Git; не переносить локальные тестовые секреты в production.
2. Сохранить стабильный `AUTH_SECRET` и настройки для восстановления отдельно от кода. Смена `AUTH_SECRET` делает недействительными ранее выданные ссылки управления бронями и коды; файл конфигурации сам по себе не входит в копию базы.
3. Настроить доступ приложения через Cloudflare совместно с владельцем, включая `APP_ORIGIN` с публичным HTTPS-адресом. Проверить сетевые порты, взаимодействие прокси и приложения и работу IP-ограничений с учётом доверенных прокси. HTTPS и режим Cloudflare настраивает владелец.
4. Проверить совместимость и условия лицензирования выбранной версии CockroachDB для production и выбранного способа копирования/восстановления. Не менять версию БД в рамках обычного обновления приложения без отдельной проверки.

### 2. Ручная полная копия и восстановление

Реализовано 2026-11-20: `scripts/db_snapshot.sh`, штатные `BACKUP` / `RESTORE` CockroachDB и восстановление в новую базу; проверка выполнена на изолированном контейнере и синтетических данных. Подробности, ограничения и команды — [DATABASE_BACKUP.md](DATABASE_BACKUP.md). Реальную production-копию и восстановление на production-сервере ещё предстоит проверить при подготовке запуска.

1. Выбрать и проверить поддерживаемый для используемой версии CockroachDB способ получения согласованной полной копии базы, включая схему, все данные, изображения и историю Goose. Уточнить, что дополнительно требуется для восстановления пользователей и прав доступа БД.
2. Подготовить ручной скрипт создания копии, понятное расположение результата и инструкцию по скачиванию через SSH. Показывать ошибку, если копия не создана; не объявлять копирование успешным только по факту появления файла.
3. Подготовить и проверить восстановление копии в **отдельную локальную базу**, без автоматической перезаписи существующей. Проверить совместимость версий и то, что приложение видит восстановленные записи и изображения. Использовать для разработки не production-сервер, а изолированное окружение.
4. Документировать, что копия содержит реальные пользовательские данные и требует ограниченного доступа. Настройку локальной почты и обработку отправок при работе с реальными данными согласовать отдельно до запуска локального приложения с такой копией.
5. Проверить и описать восстановление на сервере, включая последовательность действий при отсутствии действующей базы. Не заменять существующую production-базу без отдельного явного согласования.

Копия, оставленная только на сервере, может быть потеряна вместе с ним. Скачанная на ПК ручная копия позволяет восстановить состояние на момент её создания; более поздние изменения в неё не входят.

### 3. Обновление одной командой

1. Спроектировать скрипт для запуска по SSH: получить выбранный коммит `main`, сохранить идентификатор текущей работающей версии и номер схемы БД, подготовить новую сборку.
2. Не затирать незакоммиченные изменения, production `.env` или том БД. При ошибке получения кода или сборки завершать работу с понятным сообщением. Не использовать удаление томов или миграционные `reset`.
3. Запустить обновлённое приложение, учитывая автоматические миграции при старте API; проверить готовность сервисов и доступность приложения. Health check не заменяет проверку всех пользовательских сценариев.
4. Сообщить результат, идентификатор установленной версии и причину ошибки. Предотвратить одновременный запуск нескольких обновлений и миграций.
5. На отдельной тестовой среде проверить обновление с сохранением данных, перезапуск Docker, неуспешную сборку и неуспешный запуск. Проверить, что работающая версия и состояние схемы определяются достоверно.

### 4. Процедура отката

**Предлагается** сохранять предыдущий коммит и возможность запустить прежние образы. Если версия схемы точно не изменилась и миграции не выполнялись частично, при неудачном обновлении можно вернуть предыдущую версию приложения и проверить её готовность. Точные условия автоматического возврата согласовать при реализации.

Если миграция выполнилась или завершилась ошибкой, автоматический `down` / `down-to` не запускать: он может удалить данные, а ошибка миграции с `NO TRANSACTION` — оставить частично изменённую схему без записи об успешном применении. Скрипт должен остановиться и показать доступную информацию; дальнейшее действие определяется по конкретной миграции. Возврат старого приложения сам по себе не отменяет изменения БД.

Для обдуманного отката схемы нужны остановленный API и мигратор **новой версии**, содержащий инструкции `down` применённых миграций. После проверки совместимости запускается предыдущая версия приложения. Откат схемы не восстанавливает удалённые данные; восстановление ручной копии возвращает БД к моменту её создания и теряет последующие изменения. Не выполнять откат или восстановление production-данных без отдельного явного согласования владельца.

## Критерии готовности следующего этапа

- На отдельной тестовой среде ручной скрипт обновляет приложение из `main`, сообщает результат и сохраняет данные при пересоздании контейнеров.
- Неуспешное обновление и предусмотренный откат приложения проверены; сценарий с ошибкой или изменением миграции не запускает опасный автоматический откат.
- Ручная полная копия скачивается и успешно восстанавливается в отдельную локальную БД; проверены записи, изображения и история миграций.
- Написаны реальные команды для запуска, копирования, восстановления и диагностики; секреты не публикуются в репозитории.
- Публичный запуск, настройка Cloudflare, почты и остальные проверки проводятся отдельным этапом после подготовки и согласования необходимых параметров.
