# Ручная копия и восстановление БД

Скрипт [db_snapshot.py](../scripts/db_snapshot.py) создаёт согласованную полную копию **базы приложения** через штатные `BACKUP` / `RESTORE` CockroachDB. В архив входят схема, все таблицы, желания, изображения, аватары, бронирования и история миграций Goose. Это не SQL-файл и не полная копия кластера: учётные записи и права пользователей CockroachDB, настройки кластера, `.env` и `AUTH_SECRET` сохраняются отдельно.

Скрипт рассчитан на текущий одноузловой CockroachDB в Docker: `start-single-node`, `--insecure`, узел 1 и `--store=/cockroach/cockroach-data`. Он не меняет конфигурацию контейнера и не останавливает приложение. Нужны запущенный контейнер БД, доступ к Docker и Python 3.10+ на машине, где выполняется скрипт. Путь к Compose-файлу и архиву задаются относительно текущего каталога; команды ниже выполняются из корня проекта. CockroachDB ограничивает восстановление совместимостью версий: для начала используйте на обеих машинах одну и ту же версию образа.

Архив содержит настоящие персональные данные и секретные данные приложения, **не зашифрован** и не должен попадать в Git или к посторонним. `backups/` исключён из Git. На Linux итоговый файл создаётся с правами владельца; на Windows проверьте права доступа к каталогу самостоятельно. Для сборки и импорта скрипт также использует временный каталог на хосте и временные файлы внутри тома CockroachDB; нужно достаточно свободного места на обоих. После успешной операции временные файлы внутри контейнера удаляются. При ошибке может остаться частичная копия в контейнере: скрипт сообщает её путь; перед ручной очисткой нужно убедиться, что соответствующая задача CockroachDB завершена.

## Создать копию на сервере

В примере БД называется `wishix`; используйте фактическое значение `DB_NAME` из серверного `.env`. Выходной файл должен быть новым: существующий архив скрипт не перезаписывает.

```sh
mkdir -p backups
python3 scripts/db_snapshot.py backup --compose compose.prod.yaml --database wishix --output backups/wishix-2026-11-20.tar.gz
```

При повторном запуске укажите другое имя файла. Скрипт завершится с ошибкой, если `BACKUP`, проверка наличия копии или создание архива не прошли. Само создание копии не проверяет возможность её восстановления: эту проверку выполняют отдельным восстановлением.

Скачать на ПК можно с него же по SSH, подставив пользователя, адрес и путь на сервере:

```sh
scp USER@SERVER:/path/to/wishix/backups/wishix-2026-11-20.tar.gz ./backups/
```

Для копии локальной базы используйте `--compose compose.yaml`; для явно выбранного контейнера вместо `--compose` доступен `--container ИМЯ_ИЛИ_ID`. Скрипт не запускает контейнер БД сам.

## Восстановить на ПК в отдельную базу

Запустите локальный контейнер БД обычным способом и выберите **новое** имя базы. Существующую базу скрипт не удаляет и не перезаписывает. Параметр `--grant-user` указывает существующего пользователя CockroachDB, которому будут выданы права на восстановленную базу, схему `public` и её таблицы. Как правило, это локальное значение `DB_USER`. Скрипт проверяет наличие пользователя до восстановления; он не создаёт пользователя автоматически.

Windows PowerShell (если установлен Python Launcher):

```powershell
py -3 scripts/db_snapshot.py restore --compose compose.yaml --archive backups/wishix-2026-11-20.tar.gz --target wishix_prod_copy --grant-user wishix
```

Linux/macOS:

```sh
python3 scripts/db_snapshot.py restore --compose compose.yaml --archive backups/wishix-2026-11-20.tar.gz --target wishix_prod_copy --grant-user wishix
```

Имена БД и пользователя: строчные латинские буквы, цифры и `_`, первая буква латинская, до 63 символов. Для проверки можно подключиться к `wishix_prod_copy` через DBeaver; исходная локальная БД остаётся прежней. Подключение локального приложения требует отдельно указать восстановленную БД в его конфигурации. **До запуска приложения с production-данными отдельно согласовать локальную почту и обработку очереди писем:** в копии могут быть реальные адреса и неотправленные сообщения.

Если при восстановлении или выдаче прав произошла ошибка, скрипт не удаляет частично созданную базу и сообщает её имя и расположение временных файлов. Для повтора выберите другое имя и сначала разберитесь с состоянием предыдущей попытки. Перед удалением или заменой каких-либо существующих данных необходимо отдельное решение владельца.

## Восстановление после потери сервера

Установить Docker и совместимую версию CockroachDB, запустить новый узел, создать пользователя БД приложения и восстановить архив в **новую** базу тем же `restore --compose compose.prod.yaml ...`. Если стандартный `db-init` уже создал базу `wishix`, выберите для восстановления другое имя и настройте `DB_NAME` приложения на него. Восстановить отдельно сохранённые production-настройки, в том числе прежний `AUTH_SECRET`, затем проверить доступ пользователя и работоспособность приложения. Замена существующей production-базы скриптом не предусмотрена.

## Проверки

```sh
python3 -m unittest discover -s scripts -p test_db_snapshot.py
```

На изолированном контейнере CockroachDB v26.2.10 проверены полный цикл на схеме Wishix с миграциями 001–013, синтетические записи, бинарные изображения и аватар, чтение от пользователя приложения, версия Goose и запуск API с восстановленной базой; также проверен отказ при попытке перезаписать базу или архив. Это не проверка конкретной production-копии.

Источники: [BACKUP CockroachDB](https://www.cockroachlabs.com/docs/v26.2/backup), [RESTORE CockroachDB](https://www.cockroachlabs.com/docs/v26.2/restore).
