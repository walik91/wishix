# Транзакции сервера

Механизм находится в `server/internal/db/transaction.go`. CRUD и продуктовые репозитории в него не входят.

## Сервис задаёт границу операции

Сервис получает через Fx интерфейс `services.Transactor`:

```go
type Transactor interface {
    WithTransaction(context.Context, func(context.Context) error) error
}
```

Callback типизирован, вызывается синхронно менеджером транзакций и может повторяться при конфликте CockroachDB. Сервис не получает GORM и не собирает наборы репозиториев под каждый сценарий. Обычные зависимости сервиса остаются прежними.

Эскиз будущего сервиса с двумя репозиториями:

```go
return s.tx.WithTransaction(ctx, func(txCtx context.Context) error {
    wish, err := s.wishes.Create(txCtx, input)
    if err != nil {
        return err
    }
    return s.lists.AddWish(txCtx, listID, wish.ID)
})
```

`Create` и `AddWish` здесь только иллюстрируют вызовы; этих методов и продуктовых таблиц пока нет. Проверки доступа и другие проверки, зависящие от данных БД, тоже должны выполняться в этой транзакции.

## Репозиторий использует общий Base

Каждый прикладной репозиторий встраивает `repositories.Base` и инициализирует его через `NewBase(executor)` в своём конструкторе. Общий `*db.Executor` по-прежнему приходит через Fx; доступ к нему скрыт внутри базового типа. Пример существующего Auth-репозитория:

```go
type Auth struct{ Base }

func NewAuth(executor *db.Executor) *Auth {
    return &Auth{Base: NewBase(executor)}
}

func (r *Auth) UserByEmail(ctx context.Context, email string) (*models.User, error) {
    var user models.User
    err := r.Ctx(ctx).Where("email = ?", email).Take(&user).Error
    return userResult(&user, err)
}
```

Каждый запрос начинается с `r.Ctx(ctx)`. Этот метод возвращает новую `*gorm.DB`-сессию, делегируя выбор соединения `db.Executor.DB(ctx)`:

- Без активной транзакции возвращается сессия общего пула.
- Внутри callback возвращается сессия того же `tx`, который видят остальные репозитории.
- К обеим сессиям применяется переданный контекст, включая новый дочерний deadline или отмену.

Общий GORM-объект не изменяется. Приватный тип ключа контекста объявлен только в `db`; сервисы и репозитории не читают `Context.Value` самостоятельно. Нельзя заменять полученный контекст на `context.Background()` или обращаться к сохранённому сырому `*gorm.DB` в обход Executor: такой запрос не попадёт в текущую транзакцию.

## Commit, rollback и вложенные вызовы

Менеджер использует официальный `crdbgorm.ExecuteTx`, уровень `SERIALIZABLE` и контекст с бюджетом 10 секунд на всю операцию и повторы. Более короткий deadline вызывающего кода сохраняется; callback обязан учитывать отмену контекста. При `40001` разрешены максимум 3 повтора, всего до 4 запусков callback, с задержками 10/20/40 мс. Остальные ошибки возвращаются вызывающему коду; неопределённый результат commit сохраняется как `crdb.AmbiguousCommitError` и автоматически не повторяется.

Вложенный `WithTransaction(txCtx, ...)` присоединяется к текущей транзакции без дополнительных savepoint и commit. Ошибка вложенного callback помечает всю попытку как неуспешную: даже если внешний callback ошибочно вернул `nil`, менеджер откатит работу и вернёт первоначальную ошибку. Для частичного отката внутри операции отдельного API пока нет.

Паника вызывает rollback и передаётся выше. Если внешний callback перехватил панику вложенного callback, попытка всё равно откатывается с `ErrTransactionAborted`.

Контекст активен только во время одной попытки внешнего callback. Его повторное использование после завершения или при следующей попытке возвращает `ErrTransactionClosed`. Передача контекста другому Executor с другим корневым GORM-объектом возвращает `ErrDifferentDatabase`. Такие запросы получают GORM-сессию с ошибкой и не переключаются на общий пул.

## Правила callback

- Передавать `txCtx` во все репозитории и вложенные операции; ошибки возвращать наружу.
- Оборачивать ошибки через `%w`, чтобы сохранялся SQLSTATE для распознавания конфликтов.
- Читать нужные данные и создавать изменяемые модели внутри каждой попытки; не накапливать результаты и изменения в состоянии сервиса между повторами.
- Письма, HTTP-запросы и публикацию внешних событий выполнять после успешного завершения самого внешнего `WithTransaction`. Успех вложенного вызова ещё не означает commit. Гарантированная доставка уведомлений проектируется отдельно.
- Не сохранять транзакционный контекст для последующего использования и не выполнять параллельные запросы через одну транзакцию. Параллельные самостоятельные вызовы менеджера получают отдельные транзакции.

Механизм не заменяет проверки доступа, ограничения уникальности и проектирование атомарных запросов для бронирований и лимитов.

## Проверки

Обычные тесты входят в сборку Go-образа: проверяют вложенность, rollback, повторы и их лимит, panic, отменённый и дочерний контексты, неопределённый commit, изоляцию параллельных транзакций и защиту от чужого или завершённого контекста.

Отдельные интеграционные тесты подключаются к настоящей CockroachDB по TLS. Они используют случайные тестовые схемы `tx_test_*` и удаляют только созданные ими схемы после проверки; `public` и продуктовые данные не меняются. Проверяются commit/rollback нескольких репозиториев, вложенность, отмена и реальный конфликт двух соединений: вторая операция меняет уже прочитанную первой запись, после чего первая повторяет callback и сохраняет оба изменения. Дополнительные административные права для тестов не нужны.

При уже запущенном проекте, из корня (PowerShell или bash):

```sh
docker run --rm --network wishix_default --env-file .env --mount "type=bind,source=${PWD}/server,target=/app" --mount type=volume,source=wishix_db-client-ca,target=/db-certs,readonly --workdir /app golang:1.27.3-alpine3.24 go test -tags=integration -timeout 60s -v ./internal/db
```

Имена сети и тома соответствуют текущему `name: wishix`; при запуске с другим `-p` их нужно заменить.
