# Автозаполнение желания по ссылке — предлагается

**Статус: проект решения для обсуждения, не утверждён и не реализован.** Перенос ссылок в начало формы уже поручен владельцем; этот документ описывает следующий возможный этап. Источник обязательных правил — PROJECT.md: ручной ввод всегда доступен, автоданные получаем однократно из первой ссылки, остальные ссылки являются альтернативными местами покупки, цена ориентировочная.

## Пользовательский сценарий

1. Пользователь вставляет первую ссылку в верхний блок формы. После вставки валидного полного URL или завершения ручного ввода выполняется одна попытка получить название, изображение, примерную цену/валюту и магазин. Пустое поле можно пропустить.
2. Форма остаётся доступной во время запроса. Результат заполняет только поля, которые пользователь не менял вручную. Загруженное пользователем изображение имеет приоритет. Явная очистка поля тоже считается ручным изменением.
3. Смена ссылки отменяет устаревший запрос; поздний ответ не должен заполнить данные другого товара. Дополнительные ссылки не запускают импорт и не меняют общую цену.
4. При неполных данных заполняем найденное. Если магазин недоступен или данных нет, предлагаем продолжить вручную. Сохранение желания не зависит от успешного парсинга.
5. После первой попытки — явное действие «Заполнить по ссылке» для повтора или импорта новой первой ссылки; введённые руками значения сохраняются. Это предлагаемая деталь UX, а не утверждённое изменение продукта. Периодической синхронизации после сохранения нет.

## Где и что извлекать

Предлагается обычный HTTP-запрос из существующего Go API и разбор исходного HTML. Модуль `internal/productimport` содержит безопасную загрузку и извлечение; сервис собирает результат, контроллер обслуживает запрос. Репозиторий товаров и отдельный сервис/очередь для этого сценария не нужны. HTML можно разбирать официальным `golang.org/x/net/html`; выбор зависимости подтвердить перед реализацией.

Приоритет источников:

1. Встроенный JSON-LD `Product` и соответствующий `Offer`: `name`, `image`, `price`, `priceCurrency`. Обрабатывать массивы и `@graph`, но не загружать внешние `@context` и не выполнять JavaScript. Структуры и примеры описаны в [Schema.org Product](https://schema.org/Product) и [Offer](https://schema.org/Offer).
2. Для отсутствующих полей — `og:title`, `og:image`, `og:site_name` из [Open Graph](https://ogp.me/). Они дают название/картинку/имя сайта; наличие цены не следует из базовых OG-тегов.
3. Последний запасной источник названия — HTML `<title>`. Страницы блокировки, входа и CAPTCHA не считать страницами товара.

На странице может быть несколько товаров, вариантов и предложений. Предпочитать объект, соответствующий открытому URL, и не брать первый попавшийся товар из рекомендаций. Если цену/вариант/валюту нельзя определить однозначно, оставлять цену пустой. Не подставлять минимальную цену диапазона, цену другого варианта, условную валюту по символу `$` и не конвертировать валюты. Сумма передаётся десятичной строкой и проходит текущую серверную валидацию; неподдерживаемую точность не обрезать молча.

Магазин можно обозначить безопасным текстом `og:site_name` с запасным значением hostname. Отдельную сущность магазина и каталог товаров для этого не вводить. Исходную ссылку пользователя сохранять: редиректы и canonical не должны молча убирать выбранный вариант товара. Автоматическое заполнение описания и иных полей сверх PROJECT.md пока не предлагается.

## Контракт и изображение

Предлагается приватный `POST /api/wishes/import-preview` с `{"url":"..."}` и локалью. Он возвращает найденные поля, пустые значения для ненайденных данных и машиночитаемые предупреждения; желание не создаёт и ничего не сохраняет в БД.

Картинку загружает сервер с той же защитой, что HTML, затем обрабатывает существующим `wishimage.Processor`. Предлагается вернуть нормализованный JPEG как небольшой base64-блок (до 512 КиБ до кодирования). Vue превращает его в File/Blob и использует существующий предпросмотр и обычное сохранение желания. Это позволяет обойтись без временных таблиц, токенов черновиков и потерянных файлов; повторная проверка изображения при сохранении остаётся. Ответ приватный, `no-store`, без исходного HTML. Браузер не обращается прямо к магазину или его картинкам.

Если картинка не скачалась или не прошла проверку, текстовые поля всё равно возвращаются. Относительный URL изображения разрешается относительно конечного адреса страницы и проверяется заново, включая другой домен/CDN.

## Безопасная загрузка — обязательная часть первого этапа

Текущий сервер не делает запросов по магазинным ссылкам. Импорт добавит такую возможность, поэтому перед его включением нужен отдельный проверяемый HTTP-клиент по [рекомендациям OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html):

- Только HTTP(S), разрешённые порты, без логина/пароля в URL. Проверять IPv4/IPv6, запретить локальные, приватные, служебные, link-local, reserved и metadata-адреса.
- Проверять DNS-результаты; соединяться с уже проверенным IP, сохраняя исходные Host и TLS ServerName. Повторное независимое разрешение имени при соединении не должно позволять DNS rebinding.
- Автоматические редиректы отключить; каждый разрешённый переход вручную проходит те же проверки. Ограничить их число. Прокси из переменных окружения не должны обходить политику доступа.
- Не пересылать cookies, авторизацию или другие заголовки пользовательской сессии. URL целиком и содержимое ответов не логировать.
- Ограничить время всей операции, размер уже распакованного HTML, вложенность/число структур при разборе и число загружаемых картинок. Не доверять Content-Length и Content-Type. Не загружать произвольные скрипты, ссылки и JSON-LD-контексты.
- Те же правила применяются к изображению и каждому его редиректу. Поверх этого действуют текущие ограничения формата, файла и пикселей из WISH_IMAGES.md.
- Требовать сессию и текущую защиту мутаций Origin/custom header; ограничить частоту запросов аккаунта и общую параллельность. Конкретные лимиты предлагается уточнить при реализации; ориентир — общий deadline 10–15 секунд, до трёх переходов, HTML до 2 МиБ и одно подходящее изображение.

## Первый этап и критерии готовности

Первый этап — универсальное чтение JSON-LD → OG → title, безопасная загрузка HTML/картинки и подключение к существующей форме. Проверить на 3–5 приоритетных магазинах владельца и сохранить обезличенные HTML-фикстуры для повторяемых тестов. Поддержку конкретных сайтов заявлять по этим проверкам, не обещать любые магазины заранее.

Критерии: заполнение по первой ссылке, частичный результат, сохранение без импорта, отсутствие перезаписи ручных изменений/изображения, отмена устаревшего ответа, корректные несколько Product/Offer, отказ для опасных адресов/редиректов и чрезмерных ответов, отсутствие записей/файлов до сохранения желания. Проверять отдельно сетевую политику с управляемыми DNS/Dialer и извлечение на локальных фикстурах.

Если HTML конкретного приоритетного магазина не содержит нужных данных, сначала оценить небольшой адаптер этого домена или официальный API. Headless-браузер, внешний scraping-сервис, обход CAPTCHA и фоновое обновление цен не входят в предлагаемую первую реализацию; возможная потребность обсуждается отдельно.
