# Ручное развёртывание и обновление

Скрипт [deploy.sh](../scripts/deploy.sh) предназначен для Linux-сервера с Git, Bash, Docker и Docker Compose. Он запускается вручную после `git push` и обновляет приложение из ветки `main` удалённого репозитория `origin`. Автоматический деплой и автоматический откат миграций не настроены.

## Подготовка первого запуска

Владелец самостоятельно размещает проект на сервере: репозиторий должен быть полностью получен и находиться на локальной ветке `main`, `origin` должен указывать на нужный репозиторий, а сервер — иметь доступ для `git fetch origin main`. Одного `git fetch` недостаточно, если файлы ещё не получены в рабочий каталог: нужен также checkout ветки. Скрипт не создаёт и не меняет адрес удалённого репозитория.

В корне проекта нужен production `.env` с настройками из [README.md](../README.md). Это отдельный файл сервера, он исключён из Git. Сохраните `AUTH_SECRET`: его смена делает недействительными ранее выданные ссылки управления бронированиями и коды. Настройку публичного HTTPS и Cloudflare выполняет владелец.

Из корня проекта на сервере:

```sh
bash scripts/deploy.sh
```

Эта же команда используется для первого запуска и последующих обновлений. При первом запуске скрипт собирает frontend и API, запускает CockroachDB, инициализирует БД и пользователя, запускает приложение и ожидает готовности. При наличии БД сохраняются её именованный том и данные. Допустим короткий перерыв в работе приложения. Скрипт не делает резервную копию автоматически; ручное копирование — [DATABASE_BACKUP.md](DATABASE_BACKUP.md).

## Что делает скрипт

1. Проверяет `.env`, Docker, ветку `main` и отсутствие незакоммиченных или неотслеживаемых файлов, кроме исключённых Git. Ставит блокировку от параллельных запусков.
2. Выполняет `git fetch origin main` и обновляет локальную ветку только fast-forward, без принудительного сброса и перезаписи исключённых Git файлов. При расхождении веток или локальных правках останавливается.
3. Проверяет Compose и отдельно следит, чтобы существующий сервис CockroachDB не пересоздался из-за изменения его конфигурации, а `DB_NAME` не отличался от предыдущего приложения. Изменение версии или конфигурации БД рассматривается отдельно.
4. Сохраняет доступные образы последней успешной версии под тегами `<compose-проект>-rollback-server:latest` и `<compose-проект>-rollback-front:latest`, затем собирает новые образы. При ошибке сборки работающие контейнеры не перезапускаются.
5. Запускает или проверяет БД без пересоздания существующего контейнера и выполняет идемпотентный `db-init`. Запускает новые frontend и API. API сам применяет миграции Goose при старте; отдельный `migrate up` параллельно не запускается.
6. Дожидается Docker health checks, проверяет версию миграций и сохраняет коммит, версию схемы и идентификаторы образов в `.wishix-deploy/current`. Предыдущее успешное состояние хранится в `.wishix-deploy/previous`. Каталог исключён из Git; при первом использовании с уже запущенным приложением прежний коммит может быть неизвестен.

Скрипт запускает временную копию самого себя: если обновление заменит `scripts/deploy.sh`, уже начатый запуск завершится по версии, с которой он начался. Новая версия скрипта будет использована при следующем вызове. Проверка health checks подтверждает готовность сервисов и БД, но не проверяет весь пользовательский сценарий или публичный адрес Cloudflare.

## При ошибке

При ошибке получения кода или сборки скрипт выводит этап и последний успешно зафиксированный коммит. Рабочий каталог Git уже может содержать новый коммит, даже если приложение продолжает работать на предыдущих образах; источник истины для последнего успешного запуска — `.wishix-deploy/current`, а не только `git rev-parse HEAD`.

Если сбой произошёл во время запуска или последующей проверки, схема БД могла измениться полностью или частично: миграции `NO TRANSACTION` не всегда откатываются целиком. Скрипт **не запускает `down` и не восстанавливает базу автоматически**. Если API нездоров, он пытается остановить его, чтобы не повторять ошибочную миграцию при автоматическом перезапуске контейнера. Маркер `.wishix-deploy/incomplete` блокирует следующее обновление до проверки; он остаётся и при аварийном прерывании после начала запуска.

Для диагностики доступны:

```sh
docker compose -f compose.prod.yaml ps -a
docker compose -f compose.prod.yaml logs --tail=100 server
cat .wishix-deploy/current
cat .wishix-deploy/incomplete
```

После анализа состояния миграций и определения дальнейших действий можно вручную удалить только маркер `incomplete`, чтобы разрешить новую попытку. Не делать это до проверки: иначе при новом запуске API повторит миграции. Сохранённые предыдущие образы помогают с ручным восстановлением версии приложения, но не гарантируют совместимость с уже изменившейся БД; процедура отката кода и схемы определяется для конкретной ошибки. Не выполнять `down`, восстановление копии или замену production-данных без отдельного согласования.

При принудительном завершении процесса может остаться блокировка `.wishix-deploy/lock`. Файл `pid` содержит номер процесса запуска; перед удалением устаревшей блокировки убедитесь, что другой запуск не выполняется. Не удалять рабочий каталог состояния целиком: в нём находится информация об успешных версиях.
