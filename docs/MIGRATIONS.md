# Миграции Goose

Goose утверждён владельцем 2026-11-04. Используется библиотека `github.com/pressly/goose/v3` v3.29.0, SQL-файлы в `server/internal/db/migrations/` и отдельная программа `server/cmd/migrate`. Начальная миграция аккаунтов переведена в Goose Up/Down по этому поручению.

## Автоматический запуск

При каждом запуске API, после подключения к CockroachDB и до открытия HTTP-порта, вызывается Goose `Up`. Применяются только ещё не учтённые версии. Ошибка миграции останавливает запуск. Автоматических Down/Reset нет. Эта логика одинакова в разработке и production и работает также при перезапуске контейнера.

Историю хранит стандартная таблица `goose_db_version`. Goose проверяет версии, а не контрольные суммы SQL-файлов: уже применённые файлы не редактировать, для следующего изменения добавлять новый номер.

Программа CLI и API используют одинаковую конфигурацию `goose.Provider`, набор встроенных SQL и PostgreSQL-диалект поверх pgx. Исходники миграций включаются в оба бинарника через `go:embed`; после добавления/изменения файлов образ нужно пересобрать. Нет GORM AutoMigrate, собственного SQL-парсера или глобальной конфигурации Goose.

## Команды через Docker

Из корня проекта:

```sh
docker compose run --rm --build migrate up
docker compose run --rm migrate status
docker compose run --rm migrate version
docker compose run --rm migrate up-by-one
docker compose run --rm migrate up-to 1
```

Явные команды отката:

```sh
docker compose stop server
docker compose run --rm migrate down
```

Также доступны `down-to VERSION`, `redo` и `reset` (откат всех версий до 0). `down` откатывает одну последнюю применённую миграцию; `down-to` оставляет указанную версию. `redo` выполняет Down последней версии и снова Up. Неверные аргументы отклоняются до подключения к БД. Ошибка даёт ненулевой код завершения.

**Откат схемы не восстанавливает удалённые данные.** Down миграции `001_email_auth.sql` удаляет `auth_sessions`, `auth_challenges`, `auth_rate_limits`, затем `users`. Это полное удаление аккаунтов, поэтому такие команды выполняются только намеренно на нужной БД. В ходе разработки перехода откат проверялся на отдельной тестовой БД, а не на рабочей.

Пока API остановлен, автоприменение не мешает откату. При следующем запуске текущего кода API опять выполнит `up`. Если нужно продолжить работу на старой схеме, сначала вернуть совместимую версию кода/образа без отменённой миграции, затем запустить API.

Для production использовать тот же сервис из включённого `compose.db.yaml`:

```sh
docker compose -f compose.prod.yaml run --rm --build migrate up
docker compose -f compose.prod.yaml run --rm migrate status
```

Сервис `migrate` имеет профиль `tools`, поэтому обычный `docker compose up` не запускает отдельный CLI-контейнер; автоматический Up делает API. Явный `run migrate ...` подключает профиль и необходимые зависимости БД. Контейнер не открывает портов и получает `DB_NAME` и `DB_USER`. SMTP и `AUTH_SECRET` для миграций не нужны. Строка подключения строится внутри процесса; CockroachDB работает без TLS и проверки паролей.

Для запуска вне Docker: `go run ./cmd/migrate up` из `server/` с теми же переменными БД и доступным `db:26257`. Основной поддерживаемый способ — Docker, где это имя уже настроено.

## Переход с прежней схемы и проверка пустой БД

Начальный Up использует `CREATE TABLE/INDEX IF NOT EXISTS`. Если таблицы аккаунтов уже созданы предыдущей версией, Goose выполняет безопасный повтор и учитывает версию 1 без удаления пользователей. Старую таблицу `schema_migrations`, если она есть, новый код не читает и не удаляет. Новая история ведётся только в `goose_db_version`.

Если владелец хочет самостоятельно очистить БД и проверить создание с нуля: сначала остановить API; удалить все таблицы, **включая `goose_db_version`**; затем запустить `docker compose up -d --build`. Goose создаст таблицу истории и применит Up. Если удалить только продуктовые таблицы, оставив историю Goose с применённой версией 1, автоматический Up не создаст их заново. `status` показывает учтённые версии, а не проверяет существование каждой продуктовой таблицы.

## Новые SQL-миграции и CockroachDB

Добавлять следующий файл, например `002_add_wishes.sql`, с `-- +goose Up` и `-- +goose Down`. Версии уникальны и идут по порядку. Для DDL CockroachDB текущий шаблон использует `-- +goose NO TRANSACTION`: операторы выполняются отдельно, а Goose фиксирует версию после успеха. Бизнес-транзакции и их retry-менеджер остаются отдельным механизмом.

Без общей транзакции ошибка может оставить частично изменённую схему. Поэтому начальная миграция идемпотентна в обе стороны; новые миграции должны учитывать повтор после частичного выполнения. Для SQL с внутренними `;` Goose поддерживает `StatementBegin/StatementEnd`. Новые типы миграций следует проверять на CockroachDB, прежде чем применять к рабочим данным.

Сейчас запускается один экземпляр API. Goose по умолчанию не блокирует параллельные процессы; PostgreSQL advisory lock для CockroachDB здесь не включён. Выполнять миграции одним процессом, не запускать CLI одновременно со стартом API или другой миграцией. Перед несколькими репликами потребуется отдельное согласованное решение для сериализации миграций.

## Проверки

```sh
docker compose -f compose.auth-test.yaml run --rm go-tests
```

Тесты используют отдельный Compose-проект и публичные тестовые реквизиты. Проверяются автоматический Up, повторный Up с сохранением записей, Down → Up, переходы к версиям, стандартная история Goose и принятие старой схемы без удаления данных. Все изменения выполняются в случайных тестовых схемах. Полный набор проверок авторизации также запускается на Goose.

CLI можно проверить отдельно на той же тестовой БД (без запуска тестового API):

```sh
docker compose -f compose.auth-test.yaml run --rm --build migrate up
docker compose -f compose.auth-test.yaml run --rm migrate status
docker compose -f compose.auth-test.yaml run --rm migrate down
docker compose -f compose.auth-test.yaml run --rm migrate up
```
